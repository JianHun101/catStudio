## 2. Why — 为什么这样做

### 问题链：修复在服务端，用户看不到

a2c7f73/cff6bda/974159e 三连把「角色占位符」的替换钉在了**服务端 prompt 层与解析层**——LLM 输出、mention 解析、落库全部走真名（或原文+mentions 列）。但**前端渲染层从未替换**：ChatPanel.vue `v-html="renderMarkdown(msg.content)"` 直接渲染落库原文。落库原文是 974159e 断言④ 钉死的防伪设计（content 保留 LLM 原文），所以用户看到的吐槽猫审查消息是字面 `@架构师 请收口。`——机制全通，人看不懂。

### 纯显示层，不碰数据契约

替换必须发生在**渲染时**而非落库时——落库原文是防伪锚点（改落库 = 制造虚假记录风险）。方案：前端渲染前对 content 做只读替换，规则与服务端 `resolveRolePlaceholders` 同一套（注释互相点名，防规则漂移），`@作者` 例外保留字面（前端无触发者上下文，消息旁就有作者名，保留字面语义准确）。

## 3. Tradeoff — 放弃了什么方案

| 放弃                         | 原因                                                                                                                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 服务端落库前替换 content     | 破坏 974159e 断言④ 的原文落库防伪设计——落库应保留 LLM 原始输出，替换只属于展示层                                                                             |
| 前端实现第三套替换规则       | 规则漂移风险——服务端解析严格精确匹配，前端显示替换若与之一致，两处任何一处改动都会造成「服务端解析命中但前端显示还是字面」的隐性不一致；双处同步注释互相点名 |
| ChatPanel.vue 内联写替换逻辑 | 不可测（SFC 逻辑无单测范式）；独立 utils 纯函数走 web 纯单元测试，5 组用例全绿                                                                               |
| 前端也替换 `@作者`           | 无触发者上下文——触发者是谁只有服务端知道，前端拿不到；保留字面反而语义准确（消息旁就有作者名）                                                               |

## 4. Open Questions — 不确定的点

- **thinking 内容不替换**：:794/:892 两处 thinking 渲染点按派活单边界未动——思考过程是 LLM 原始文本，不含审查结论，保留字面无用户困扰；若未来 thinking 里出现占位符，需评估是否纳入。
- **agent 改名后的历史消息**：替换是运行时从 `store.agents` 取真名，改名前落库的历史消息会按**当前**名渲染（旧名不再显示）。这是纯显示层可接受的语义——历史消息显示"现在这个角色是谁"比"当时是谁"更符合用户认知；且改动仅影响显示，落库不变。
- **store.agents 加载时序**：agents 尚未加载完成时为空数组 → 全部保留字面，天然降级（第 5 组用例钉死）；加载完成后 pinia reactive 驱动重新渲染。
