## 二、契约（**本票钉死**）

### 2.1 判据

输入 = 两侧 ref（主仓库侧通常 `dev`，会话侧 `session/<sid>`）。

1. `base = git merge-base <A> <B>`
2. `ΔA` = A 侧 `base..A` 触及的文件集合；`ΔB` 同理
3. 对每个 `f ∈ ΔA ∩ ΔB`：
   - `blobA = git rev-parse <A>:<f>`，`blobB = git rev-parse <B>:<f>`
   - **报警条件**：`blobA === blobB` **且** 两侧**各有 ≥1 笔提交**触及 `f`
4. 输出每条命中：文件路径 + A 侧 sha + B 侧 sha；命中 ⇒ `exit 1`，无命中 ⇒ `exit 0`

**为什么 `blob 相同` 是必要条件**：blob 不同 = 正常 merge 面（3-way 走真合并），无需报警；
blob 相同 = 「同一份内容被写了两遍」，merge 会**静默吞掉一笔**——这正是要抓的形态。

```js

 * @param {{ refA: string, refB: string, cwd: string }} args
```

CLI：`node scripts/closeout-dupcheck.mjs --a <ref> --b <ref> [--cwd <path>]`（默认 `cwd = process.cwd()`）。

### 2.2 纪律（写进 `CONTEXT.md`「流程约定」，逐条可 grep）

- **判据是「每份文档只有一个写入方」，不是「只有一个写入位置」**（2026-09-16 收口时更正，
  见 `docs/run/precommit-scope/closeout.md` §四）：
  - **一般 docs**（含 `CONTEXT.md` 自身、`docs/adr/`、`docs/plans/`、票面）：写入方 = **会话
    worktree**（跟代码同分支那条）；主仓库工作区**不直接编辑 docs**，只做 ff-only 合并。
  - **收口记录**：写入方 = **收口方，写在 dev 上，且绝不回写 worktree** —— 它是 **post-merge
    产物**（记录的就是合并本身），物理上不可能先于合并存在于被合并的分支里。一个写入方 ⇒
    结构上不产生重复落盘。
- 收口前跑一次 `node scripts/closeout-dupcheck.mjs`；有命中 ⇒ **先裁定保留哪一侧，再合并**。
  **判据注释里必须写明上面那条「收口记录」豁免**，否则「两侧同名文件」的机械扫描会把收口记录
  误报成重复落盘（收口记录按设计就只该出现在 dev 一侧——它不会命中，但注释要讲清为什么）。

## 三、验收（逐条可执行，实施者须留痕）

- **V1 受控正例**：一次性临时仓，两侧对同一文件写**相同内容**各一笔提交 ⇒ 命中该文件、`exit 1`。
- **V2 反例·blob 不同**：两侧同文件写**不同内容** ⇒ **不**命中（正常 merge 面）。
- **V3 反例·单侧**：只有一侧提交该文件 ⇒ **不**命中。
- **V4 反例·无交集**：两侧改不同文件 ⇒ **不**命中。
- **V5 反向对照**：把判据里的 `blobA === blobB` 改成 `!==` ⇒ **V1 必须变红**（证明判据非恒真）。

## 决策留痕

### 为什么不是「让 git 别静默」而是「显式对账」

3-way merge 对「两侧改成同一内容」返回干净结果，是 git 的**正确行为**（内容确实一致），不是 bug，
**没有可改的 git 开关**。所以只能在合并前显式对账——这是**判据面与合并面的错位**，不是配置问题。

### 为什么纪律的判据是「写入方」而不是「写入位置」（2026-09-16 收口时更正）

票面初版写的是「docs 只在 worktree 写，**要补收口记录 ⇒ 也回 worktree 分支写**」——**这条对收口
记录不成立**。收口记录生在合并**之后**，被合并的分支里不可能先有它；要它满足「只在 worktree 写」，
只能先写进 worktree、再为一行文档单独开一次 PR——**用流程代价去圆一个本来就不必要的约束**。

真正要防的是「同一份内容有**两个写入方**」（两侧各写一遍 ⇒ blob 相同 ⇒ 3-way 静默吞一笔）。
一个写入方 = 一个写入位置，「收口记录由收口方写在 dev」并不违反它。

**教训**：约束写宽了，就会长出一条没必要的绕路——与 `precommit-scope` 那张票同一个病
（粒度错，不是原则错）。

### 为什么有纪律了还要留脚本

纪律靠人记，脚本靠跑。本仓对「无落点预留会腐烂」有明确立场（QUEUE_UPDATE 标本），
其反面同样成立：**有落点 ≠ 会被消费**——故脚本必须挂在**收口链**上（`CONTEXT.md` 写死为收口前置动作），
否则它和不存在没有区别。
