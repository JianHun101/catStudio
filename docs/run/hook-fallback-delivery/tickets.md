## 票 A：`decideHookDelivery(null)` 由「投」翻转为「静默」

### 为什么

`null`（探针超时/不可达/响应不可解析）**不是随机噪声**——它最容易发生在 server 正忙着跑那只猫时，
而那个状态的字面意思就是「有归属」。故这一格是**系统性地把「本该静默」判成「投」**，
投出的还是 Why/Tradeoff/OQ 全是 TODO 的**空壳**（猫补填后还会再投一份完整版，
两份内容不同 ⇒ 过不了内容去重 ⇒ 审查者收到两份）。

这一格想覆盖的场景（有归属的猫没自己投 → 补投）已被**收尾兜底闸**（`--fallback-sha`）在更对的时刻、
用更对的判据（回复 mentions 是否含审查者 = 投递本身，而非投递的代理量）覆盖。
⇒ 钩子在此刻做不了这个判断，**让位**，不是「把判据做准」。

（根因论证与四态取证见本会话历史；此处只留结论。）

## 票 P3（同票带）：补投来源标记在「二次瞬态失败」下仍保住

### 为什么

`drainPending` 以 `pendingSrc: entry.src` 原样透传（`:1726-1727`）。
若这一轮**又**瞬态失败，重记入的条目必须保住来源标记——src 一旦退化成 `legacy`/`hook`，
下一轮 drain 就会把**兜底条目**当 hook 条目去判归属 ⇒ 判静默砍掉 ⇒ `ef8c752` 修好的安全网又断。
**这条测试是该安全网唯一的报警器。**

现有 e2e 14i 只覆盖「失败一次 → drain 成功」，未覆盖「drain 里再失败一次」。

### 契约

- **P1** 新增 e2e：`src='fallback'` 条目在 drain 补投时**再次**瞬态失败 ⇒ 仍在 pending 且 `src === 'fallback'`（不得退化）。
- **P2** 同款覆盖 `src='gate'`（`deliverHeadIfUndelivered` 的 `pendingSrc: 'gate'`）。
- 不动 14i 现有用例。

## 挂账 G1（用户裁「先记得」，**不立项**，勿随本活收口删除）

**「execute crash」这个标签名不副实。**

- 读数：`1107` 次执行 / `84` 次失败（7.6%），其中 `execute crash` **11 次（1.0%）**。
- 签名：11 条的 `error_message` 全是字面量 `execute crash` —— 即 `serial.ts` 的兜底串
  （`execError instanceof Error ? execError.message : 'execute crash'`）⇒ **都不是被 catch 到的 Error**。
  同期的 `spawn ENAMETOOLONG` 证明这条路会写真话，不是恒填兜底串。
- 日志侧：这 11 次的前一行全是正常事件（`agent reply done` / `review fallback judged` / `agent-to-agent dispatch`），
  **无 stderr、无非零退出**；crash 行的 `ended_at` 与同 trace 兄弟执行的 `completed` **重合到秒**，紧接 `queue → next`。
- 抽查 4 条：失败区间内该猫**落库消息数为 0** —— 猫跑了 2.5–10 分钟，产出没落地。
- **推断（未定根因）**：`executeRun` 的 finally 发现槽位仍 busy，用兜底串把行盖成 failed，顺手把回复丢了。
- 实害：1% 的执行静默吞活，而「崩溃」听起来像正常损耗，不会有人去查。
- 处置：用户裁「出现率很低，先记得」。**再次出现（用户报「猫没动静」）时优先查这条**，
  查法：`execution_logs` 里 `status='failed'` + `error_message='execute crash'` 的行，
  比对 `triggered_by_message_id` 对应 trace 下是否有 `completed` 兄弟行；回复是否落库看 `messages`。
