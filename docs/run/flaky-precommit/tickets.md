# 票：pre-commit 全量闸的 flaky 用例加固

> 归属：提交门禁可靠性（独立于 T-2）。
> **立票 2026-09-15**（用户指令：「立 flaky 测试」）。
> **现场**：`packages/server/src/memory/embedding-client.test.ts:864`。

---

## 结论先行

1. 该用例**已实测 flaky**：单跑绿、全量并发跑偶发红。
2. **危害被 worktree 化放大**：`.husky/pre-commit` 末行是**全量 `pnpm test`** ⇒ 任何 flaky 红 = **挡死任意猫的任意提交**；T-2 落地后每只猫各跑一遍全量 ⇒ 触发概率 ×N。
3. 本票**只治这一条**，不重构门禁形态（是否把 pre-commit 全量收窄为「只跑受影响包」另议）。
4. **红线**：不得以放宽断言（`expect.anything()` / 删断言 / 加 retry）方式「修」——那会把真 bug 一起埋掉。

---

## 一、现场

用例（`embedding-client.test.ts:864-875`）：

```
live 已被 drop（失败即杀进程）⇒ 退到 lastSuccess 的握手端口、killedChild=false
```

末行断言：`expect(client.stop()).toEqual({ port: stub.port, killedChild: false })`

嫌疑点（**待证，不是结论**）：

- `killedChild` 依赖失败路径 `dropSidecar` 是否已完成杀进程——若存在异步竞态，live 未清则 `killedChild` 变 `true`。
- `makeStub()` 的端口分配在多测试并发下是否可能碰撞——同文件 `:849` 已有 `not.toBe(9999)` 的防御性断言，提示作者已察觉端口面。

---

## 二、验收

| 编号 | 判据                                                                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| F1   | **先复现**：给出至少一次真实失败的证据（命令 + 输出 + 时间）。**若穷尽手段无法复现，须给出机制分析并说明为何判定为 flaky**——不接受「复现不了就改断言」 |
| F2   | 定位到确定性根因（时序 / 端口 / 资源竞争），以**最小改动**消除                                                                                         |
| F3   | 加固后：单文件重复跑 ≥20 次全绿                                                                                                                        |
| F4   | 加固后：全量跑 ≥3 次全绿                                                                                                                               |
| F5   | **反向对照**：人为注入原竞态条件 ⇒ 用例必须变红（证明判据仍有效、没被改弱）                                                                            |
| F6   | 全量闸绿（`pnpm lint` + `pnpm test`）                                                                                                                  |

---

## 三、红线

1. **不改 `.husky/pre-commit` 的门禁形态**（本票不碰门禁策略）。
2. 不删断言、不放宽断言、不加 retry / 重试掩盖。
3. 提交限定路径；开工前确认无并发实例（`git status` + `execution_logs` 同 agent 时间窗）。
4. 本票**只动测试代码**——若根因在生产代码（如 `embedding-client.ts` 真有时序缺陷），**停下报店长**再定，不要顺手改生产逻辑。
