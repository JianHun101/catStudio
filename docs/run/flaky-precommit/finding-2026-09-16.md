> 归属：`docs/run/flaky-precommit/`（本票根因结论）。

> 结论由**店长独立复现**关键判据后固定；探针原始产出在 `workspace/flaky-probe/`（gitignore，未进仓）。

## 结论先行

`listen(0)` 让 OS 随机分配端口，**偶尔会分到 WHATWG Fetch 规范的「禁用端口」黑名单**里的端口。服务**真的在监听**（裸 TCP `CONNECT-OK`、`listening:true`），但 `fetch` 在发请求**之前**就被 undici 拒绝：

```
cause = "bad port"     ← 连 TCP 都不建，永不恢复
```

而正常失败长这样：

```
cause = "ECONNREFUSED" ← 端口无服务，快速失败，可恢复
```

两者**性质完全不同**。撞上黑名单端口后，被测的重试路径会吃满 `PROBE_TIMEOUT_MS = 30_000`，**撞穿 harness 的 10s 预算** ⇒ `Test timed out`。

⇒ 这条**不是时序竞态，是端口分配的确定性缺陷**——只是触发取决于 OS 恰好分到什么端口，所以表现为「偶发」。

## 三、现场行号纠正

票面 §一 写的现场是 `embedding-client.test.ts:864`。实际失败的一手证据（上一轮提交被挡时的 vitest 输出）：

```
FAIL |@cat-study/server| src/memory/embedding-client.test.ts > 票午 (b) 批次失败自动重试一次
     > 重试有界：两次都失败 ⇒ 恰好两次请求，不是无限重试
Error: Test timed out in 10000ms.
```

⇒ **真凶在 `:311`「重试有界」**，不是 `:864`。同类失败另打到 `scripts/flywheel/scan.test.js`（「首败 + 重试成功」，同样是重试路径）。

**为什么是重试路径的测试最先红**：这些测试用的是**模块默认预算**（`PROBE_TIMEOUT_MS` 30s / `REQUEST_TIMEOUT_MS` 10s），而 harness 预算是 server 10s / scripts 5s —— **默认预算 ≥ 框架预算**，一旦命中黑名单端口就必然撞穿。

## 四、生产侧同病 —— 红线 4 触发，**停下报店长**

`scripts/flywheel/embed-server.mjs:285`：

```js
listen(process.env.EMBED_SIDECAR_PORT || '0')
```

**默认 `0` = OS 分配**，与测试 stub 同源 ⇒ sidecar 可能起在黑名单端口上。后果比测试 flaky 严重：主进程经 HTTP 调 sidecar（`retrieveMemoryContext` → `searchChunksHybrid`），**fetch 永久 `bad port`** ⇒ 嵌入功能整体静默失败。

flash猫 按票面红线 4（「若根因在生产代码，停下报店长」）**未动生产代码**，只报。

## 五、修复方向（待派活，非本文件结论）

1. **测试侧**：stub 端口分配避开黑名单（分配后校验，命中则重取；或从安全段内挑）。
2. **生产侧**（优先，另立单）：`embed-server.mjs` 端口分配同款加固——`EMBED_SIDECAR_PORT` 指定值也要校验，`0` 分配后同样要校验。
3. **加固后的反向对照**（验收 F5）：把 stub **强制绑到黑名单端口**（如 1719）⇒ 用例必须**仍然红**，证明判据没被改弱。

## 六、本轮的教训（派活侧）

定位轮撞 30min 硬超时，**根因是票面把「复现 + 根因 + 修复」塞进一张票，而「机制分析」没有收敛边界** —— 该轮写了 8 个探针（`probe.mjs` → `probe8.mjs`），最后一个去扫 1..49151 端口拿「权威黑名单」时卡死。

**权威黑名单对修复并不必要**（见 §一：对候选端口做 fetch 即可判别，无需全表扫描）。后续同类票应在票面写明**机制分析的收敛条件**（如「拿到 `err.cause` 即停，全表扫描不必要」）。
