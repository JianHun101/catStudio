段瀑布：同一跳，拆成 11 段

「细化为段瀑布」指的就是这个——同一根时间轴，把一次执行拆成 11 个可命名的段（R2 已落库）， 每段有自己的起点与时长。横向位置 = 它在执行的哪一刻开始，横向长度 = 它占了多久。 组与组之间的斜纹是编排空档（代码在两个段之间的纯 JS 开销，不归属任何一段）。

为什么放这儿合适
面板已经在显示「谁在忙 / 排了几条队」。trace 是同一件事的下钻：这只猫现在到底卡在哪一步。不用跳页。
分段条（我推荐）
就是现有两段条的九段版——一根 100% 堆叠条，边界即段界。改动最小、误解最少，而且它保留了「编排挤在开头、落库挤在结尾」这个顺序信息。
排行条：切换后请看它的失败
按时长降序 + 归一到最大值。看着合理，实测当场破产：llm.chat 168.6s 当分母，第二名 1.16s 只有 0.7%，其余全是 0 像素——表里只剩一行。这条已从候选里划掉。
真瀑布（切换）
保留偏移与空档，回答「卡在哪一步」。代价：段名截断成 context.as…，8 个小段挤在左边缘。300px 下它能站住但不好读。
300px 的硬限制
要舒服地看瀑布，得给它更宽的画布——链路 tab 那根 720px 的轴（②），或点开一个抽屉。
没画的东西
这里没有时间轴刻度、没有缩放、没有跨跳叠加、没有 hover 详情卡。原型只证明「段数据在 300px 内可读」，不证明它该取代链路 tab。

↑ 进行中态（左）与完成态（下）
绝不画成 0 或空白
P1-B 已为「null ≠ 0」立过判据：没数据必须显式说「采集中」，不能是一条空条——否则会被读成「这段耗时为 0」。
值不值得做成实时
做实时 = server 在每段开始/结束时推 socket 事件。那不是 R2 的现有能力（R2 是收尾一次写库），要动 server 事件面，属新票。
实时能买到什么
一次执行约 3 分钟。盯着一根段条从左往右长，能回答「它是不是卡住了」。但「卡住」现在面板上的忙碌态已经说了一半。
原型默认取的立场
先做后视镜（跑完才看）——零 server 改动、马上能用，且已经能回答「170 秒里哪一段吃掉 99%」。实时单独立票。
