⑤链路数据是怎么来的 · 超时怎么判断 · 数据什么意思

Q1 · 评估里的链路数据是怎么来的？
一句话：不是新采的，是把已有的两张表按一个键重新分组算出来的。
  • 取数（一条 SQL，executionLogs.ts）：execution_logs 左连 messages 两次——一次连「回复消息」、一次连「触发消息」，算出 chain_id = COALESCE(回复消息.task_id, 触发消息.task_id)。
  • 分组：同一个 chain_id 的执行行 = 一条链；链内每一行 = 一跳。 锚为 NULL 的行是孤儿跳，单独放 orphanChain，不进链列表（dev 库实测约 2.6%）。
  • 变换（chain-query.ts，纯函数、零 I/O）：算每跳的段、打四个卡点标记、按链跨度降序排。 HTTP 只做「取数 → 调纯函数 → 返回」（GET /api/eval/chains）。
  • 为什么这个键：只认触发侧会丢 32.5% 的行，只认回复侧丢 7.5%，取两者合并（覆盖率 97.4%）。 这是已裁死的口径，不是实现细节。
  • 另一类数据不同源：段分解（本原型的瀑布）来自 R2 新加的 spans 表， 按 execution_id 挂；它的 chain_id 就是上面那个值——两边能对上。
Q2 · 超时是怎么判断的？
不是「超过某个时间就算超时」。评估里有三个互不相干的东西容易被当成同一件事：
  • ① 真超时（执行体层面）——由调度器判定，写进 execution_logs.status='failed' + error_type，错误文案是「执行超时 (Ns)」。触发源有三条：dispatch 硬超时 AGENT_HARD_TIMEOUT_MS（默认 30min）、CLI 空闲超时（默认 20min）、网络超时。 分类器 classify-error.ts 把带这些关键词的错误归进 timeout 桶。
  • ② 超时率（L1 只看这一个数）——timeoutRate = timeout 条数 ÷ (completed + failed 中 error_type≠server_restart)， 近 30 天窗口，告警阈值 EVAL_ALERT_TIMEOUT_RATE 默认 10%。 分母刻意排除了 server_restart——重启杀死的行是 infra 桶，算进成功率/超时率会冤枉模型。
  • ③ 「慢」标记（链路页那个 slow 徽章）——这个跟超时无关。 它是一条纯阈值线：totalMs > EVAL_CHAIN_SLOW_MS（默认 300000ms = 5 分钟）就标。 它不判失败、不判超时，只是「这一跳值得看一眼」。所以一次 成功但跑了 6 分钟的执行， 会同时带 slow 而 status 仍是 completed——这是设计如此，不是矛盾。
一句话记法：status=failed + error_type=timeout 才是超时； slow 只是慢；EVAL_ALERT_TIMEOUT_RATE 是拿前者算比例、发告警。
Q3 · 数据意义是什么？（每个数字在说什么）
  • 链（chain）——一次「用户提问 → 猫A回 → 猫B接 → …」的完整协作回合。 spanMs = 链内最早开始到最晚结束的墙钟跨度。注意：链里有在飞跳时它是下界（偏小）。
  • 跳（hop）——链里一只猫的一次执行。status 是完成/失败/进行中。
  • 三个耗时口径，别混：
    · totalMs = ended_at − started_at，两列都是 UTC 字符串、精度 1 秒 → 必是 1000 的整数倍，不是毫秒精度。
    · replyMs = latency_ms，进程内毫秒计时 → 真的毫秒； 语义 = 上下文过滤 + 记忆检索 + LLM 流式 + 落库，不只是 LLM。
    · nonReplyMs = 两者相减、钳到 ≥0。名字刻意用中性词——它包含等 token 锁和建行开销， 不含等锁之外的东西也说不出，所以不叫 lockWaitMs。
  • 举个真例（就是上面那条执行）：execution_logs 说 237.000s（秒级）， spans 根段说 236.710s（毫秒级）——差 290ms 全是精度，不是错。
  • 四个卡点标记（可同时出现，不互斥）： failed 失败 ／ no_reply 结束了但没回复（或回复 0 字）／ slow 超阈值 ／ no_data 完成了却没有耗时记录（采集修复前的存量行）。
  • 段（span）——一次跳内部的分解，回答「这 236 秒花在哪」。口径铁律： 执行总时长只认根段 invoke_agent，禁止加总子段—— git.auto_commit 是轮次段挂在根段下、时间窗在根段之外，加总会算到 >100%。
  • 它回答了什么（这是这套数据的全部价值）：地图上的问题③「哪里耗时最长」， 在链路粒度只能答到「哪一跳」，在段粒度才能答到「哪一段」。真例： llm.chat 占 99.4%，而首字只等 3.39s（1.4%）—— 不是等第一个字慢，是吐完所有字慢。这句话在段数据出现之前算不出来。
