实测挖到一条真缺口（本原型的副产物，值得单独立单）：dispatch.queue_wait 是 挂在执行根段下、但时间窗完全落在根段之外的段——它量的是「消息在 Agent 队列里等了多久」。

实测两例：374f58f0 排队 151.97s + 执行 159.70s；0d643aaf 排队 109.33s + 执行 60.81s。

而 execution_logs.started_at 记的是根段起点（03:05:05），不是排队起点（03:02:33）—— 也就是说：用户真实等了 312 秒，而现有每一个耗时口径都只报 160 秒。排队时间不进任何口径。

这与 R2 票面已记的 git.auto_commit 是同一类（轮次段挂根段下、窗口在根段外）。

已裁决：不计入本次执行——它量的是「上一跳还占着槽位」的那段时间，属 两跳之间的间隔。本原型的处理是画都不画：段条与段清单里都没有它， 只在 trace 末尾留一行文字注解。

但不能让它静默消失——「用户等了 312 秒、系统每一处都只报 160 秒」这个偏差 得有人解释；静默比画错更坏，那正是这张红框存在的理由。
另两条真机观察（不阻塞本单，登记备查）： ① span_llm.max_tokens=2048 而 output_tokens=2380 / 2753——输出超过记录的上限， 可能是记的是请求值而非生效值； ② 43 次执行里 llm.chat 的 status 出现过 1 次 timeout、 memory.retrieval 也出现过 1 次 timeout（同一次执行 77a34bfc）。
