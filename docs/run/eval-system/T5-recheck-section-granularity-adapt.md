## 一、缺口（实测，不是预测）

T4 把末次截断从「按**片**」改成「按**节**」后，本脚本的一条**承重自证**被打断。实跑一次
（`--no-live-rewrite`，命令见 T4 §九）：

```
[eval:retrieval:recheck] 拒出报告：合并序重建与链段 self-reported final 流水不符 14 条
                         ——重建序不自证，名次/分差读数不可信
{"ok":false,"phase":"remerge","offenders":[{"id":"G05","mismatches":[
  {"kind":"rank","chunkId":907,"chain":1,"rebuilt":4}, ...]}, ...]}
```

**这个闸判得对**——不是误报。它守的正是「重建序 == 链段序」，而**重建侧没跟上生产语义**。

## 二、机制（核到行，`dev@8acb4101` 实测）

- `mergeQueryPools`（`scripts/eval/retrieval-attribution-recheck.mjs:400`）把「注入集」硬编为
  `order.slice(0, topK)`（同文件 `:430`）——**片级**语义。
- `verifyMerge`（同文件 `:445`）逐行核 `rebuilt.rank === chain.finalRank`。
- 改动后链段的 `finalTraces` 是**按节去重**后的代表片，其在**原始合并序**里的下标必然带空洞
  （`chain:1` vs `rebuilt:4` 正是「中间 3 片被同节去重吃掉」的指纹）⇒ 逐行核**必不符**。

## 三、✅ 店长架构裁决（2026-09-21）：取**形态①**

T4 §8.3 给了两条备选：

- **①** 重建侧跟生产走：注入集也按节去重后再编号。
- **②** `verifyMerge` 改核「集合相等 + 序一致」而非逐行下标。

**裁①**，三条理由：

1. **重建侧必须复刻生产语义**。`verifyMerge` 的存在意义是「重建序 == 链段序」的**独立自证**；
   生产已按节去重而重建侧不去重，它衡量的就不是生产。
2. **取② = 放宽判据以适配实现**，正是本仓反复吃过的「**探针宽度大于判据宽度**」形态
   （同一族已在 P0 集成层 / R12 计数 / T3-P3 四条上现形）。判据一旦放宽，重建侧将来**再偏也不会红**。
3. **①不降强度**：逐行下标核原样保留；②的「集合相等 + 序一致」在实现上极易退化成弱判据。

**①的代价（明写，须在产物里交代）**：§五「差几名」的口径由「**片**名次」变为「**节**名次」。
