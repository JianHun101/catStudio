## 一、问题

`parseFloat(process.env.X || '默认')` 在 `X` 被设成**非数字**（如 `abc`）时返回 `NaN`，而所有消费点都是 `<` / `>=` 比较 —— **`NaN` 参与的比较恒为 `false`** ⇒ 阈值形同被禁用，且**无任何日志**。

用户配了 env、以为生效了，实际该告警的一条都不告 —— **假绿门**，与本项目「消灭静默通过」的靶心同类。

**漏因未坐实，不硬下结论**：本仓有「GNU grep 静默跳过含 NUL 字节的文件」的先例（`map.md:67` 记 `memory/index.ts` 曾有字面 NUL），一度疑似此因；

**计数终值（2026-09-23 收口复核，ds猫）**：落地 PR #140 时接线 **7 处**（= 本表口径）；其上另有 **2 处后续票主动并轨**，族面现为 **9 处**。两处**均非漏改**，是收敛方向。口径差的完整说明见 **§八.2**。

## 三、根因链（为什么熔断没兜住）

`env.ts` 对这批变量用 `??=` 兜默认值 —— 但 `??=` **只兜「未设置」，不兜「设成非数字」**：

```
EVAL_ALERT_SUCCESS_RATE=abc
  → env.ts 认为「已设置」，跳过默认值
  → parseFloat('abc') = NaN
  → m.successRate < NaN = false
  → 不告警，且无日志
```

即：**熔断点选错了层**（选了「有没有设置」而非「解析后是不是有限数」）。

## 四、修复方案（建议，实施者可在票内复议）

`sampler.ts:23-25` 的写法即样板，抽成共用小工具后逐处套用：

- `Number.isFinite(raw)` 为假 ⇒ **回退默认值**（不是回退 0 —— 0 会改变语义：`slowMs=0` 会把每一跳都标 slow，是另一种假数）；
- 回退时**打一条 warn 日志**（含变量名 + 原始串 + 回退值）——「静默」本身就是这个 bug 的一半，修了值却不留痕等于只修一半；
- 可（非必须）加下界钳位：阈值类 > 0、比率类 ∈ (0, 1]。

## 五、边界

- **只改解析与回退**：不改任何阈值语义、不改默认值、不改告警状态机、不改 DDL。
- 七处消费点**各自独立**，可一笔提交（同族同因）。
- 不动 `env.ts` 的 `??=`（那是「未设置」层的正确兜底，两层各司其职）。
- **第 7/8 处额外边界**：不改 `currentRetrievalParams()` 的返回结构（`RetrievalParamsSnapshot` 三个字段是检索链与 `reply.ts` 共用的契约快照，只换解析方式，不改形状）。
