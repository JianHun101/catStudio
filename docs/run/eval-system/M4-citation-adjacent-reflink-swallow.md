# M4 角标缺陷修复：相邻引用 `[1][2]` 被引用式链接排除式误伤

状态：已立项，待派活（用户 2026-09-27 拍板「1 派」）

## 一、背景（活库实测证据，非推测）

2026-09-27 真机排查「`[1]` 没变上标反而成了正文」，扫最近含 `[1]` 的 17 条回复逐条对 `/memory-refs` 读口，落三个桶：

- **桶 A（本票对象）**：相邻引用被吃掉前一个。实证：店长回复 `35da71fb`（2026-09-27 02:05）正文「注入的 `[1][2]` 是谁」为纯散文（不在代码块/内联码内），读口返回 `markers=[2]`——`[1]` 消失，前端渲染成普通正文。
- 桶 B：代码/反引号内 `[1]` 不渲染——设计如此（进 `markersInCode` 诊断列），非缺陷。
- 桶 C：A2A 触发回复 `state=not-retrieved, reason=skipped-a2a`——设计如此，非缺陷。

## 二、根因（两侧源码已核）

角标判据正则两侧同式：

- server：`packages/server/src/memory/citationMarkers.ts` 的 `CITATION_PATTERN` = `\[(\d+)\](?![([:])`
- web：`packages/web/src/utils/markdown.ts` 的 inline tokenizer 同款排除式

排除式 `(?![([:])` 防的是 markdown 链接三形态（`[1](url)` 内联链接、`[1][ref]` 引用式链接、`[1]:` 链接定义）被角标拆散。但「`]` 后跟 `[` 即排除」写得**过宽**：`[1][2]` 恰好长成引用式链接的形状，`[1]` 被误伤；而真实的引用式链接几乎不用纯数字做 ref 名。「同一处连引两条」是自然引用方式，判据与之冲突。

## 三、修法（裁决方向，实现细节归实施猫）

排除式收窄：**`]` 后跟 `[` 时，仅当方括号内不是纯数字引用形态才当链接排除**。即 `[1][foo]` / `[1][]` 仍按链接处理（`[1]` 不计入），`[1][2]` 两个都计入引用。参考形态：`(?!\(|\[(?!\d+\])|:)`——实施猫可调整，但行为判据以 §四 验收为准，且**前后端两处必须同批改、语义逐字一致**（票面既有纪律：两侧同一条排除式）。

已知边角（裁决：接受，不修）：`[1][2foo]` 这类「数字开头但非纯数字」的 ref 名下 `[1]` 不计入——真语料未见，防御成本大于收益，注释留一句即可。

## 四、边界

- 只动排除式本身与两侧测试；`markersInCode` 诊断列语义不动；代码块/内联码豁免不动；链接三形态的正常排除必须保持（回归面）。
- 不改渲染产物形态（`sup.mem-citation` 结构不动）、不动路由契约。
- 复述面同批：两侧正则的注释/头注里对该排除式的描述（如有）同批对齐。
