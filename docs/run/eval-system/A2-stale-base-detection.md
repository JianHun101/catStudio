## 二、机制（核到行）

- worktree 的基点 = **分支创建那一刻**的 `dev`；并行链上 `dev` 继续前进。
- 已记形态：**worktree 看不见未跟踪产物**。本轮补的是**第二形态**——
  **已跟踪文件在旧基点上同样盲**（该文件在 `dev` 上已改，但在被审树上还是旧的）。
- 危害有三类，第三类最重：
  1. **假缺陷**：提重复票（第 1/2/3 次都提了「立票」建议，店长三次都判「不立票」）。
  2. **假读数**：报告里的事实陈述过期，且**作者与审查者互相印证**，靠单方复核发现不了。
  3. ⚠️ **真风险：合并可能把 `dev` 上的修复打回去。** A1 险些踩中——其基点不含
     `43b90d5a`，而 A1 与被修的文件是**同一个** `reply.test.ts`。收口时靠
     `git merge-tree --write-tree dev <tip>` 干跑才排除（结果：修复幸存、无冲突）。

## 三、候选形态（**待 grilling，不在此裁**）

|     | 做法                                     | 已知问题                                                           |
| --- | ---------------------------------------- | ------------------------------------------------------------------ |
| 甲  | 派活单要求开工前 `git rebase origin/dev` | 与收口纪律冲突：rebase 重写 sha，「已审 sha 字面量」的载体链就断了 |
| 乙  | **发起审查前**做落后检测                 | 待定判据（见下）                                                   |
| 丙  | 收口时检测                               | **太晚**——审查成本已花掉，且假缺陷已写进报告                       |

**倾向乙**，且判据不该是裸的「落后几笔」（并行仓库里恒真、必被当噪声忽略），
而是**交集**：

> `git diff --name-only <base>..origin/dev` ∩ `git diff --name-only <base>..<tip>`
> **非空** ⇒ 该文件在两条链上都被动过 ⇒ 必须在**当前 `dev`** 上复验，并把复验结论
> 写进报告。

A1 用这条判据会当场命中（双方都动了 `reply.test.ts`）；T5 那次同理。这条判据的
可证伪性也干净：给一对「基点落后但无文件交集」的分支，它**必须不报**。
