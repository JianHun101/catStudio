## 一、要解决的问题（证据全部来自 T3 已复现读数，不重跑不复述推测）

| 归因           | 处数 | 含义                                                              |
| -------------- | ---- | ----------------------------------------------------------------- |
| `not_topk`     | 9    | 片进池了、阈值也过了，**只是排序没排进注入集**                    |
| `below_topk`   | 1    | 被召回过，输在跨查询合并的截断                                    |
| `not-recalled` | 1    | **已订正**：不是覆盖洞——向量通道够得着（生产面还排到过 `rank=0`） |

## 二、为什么值得做（理由和多数项目相反）

一般项目上 rerank 是「上了但证明不了有用」。**本项目里证明链是现成的**：

- 黄金集 40 条（R9，锚点保鲜 + 冻结改写器）— `docs/eval/retrieval-golden.json`
- 跑批脚本，两指标 + 负例判红单列 + canary 尺子自证 — `scripts/eval/retrieval-baseline.mjs`
- 归因三分类 `not_topk / below_topk / not-recalled` — 且 T3 已把 11 处**逐条名次与分差**列出来了

⇒ 本票能出「**recall 从 X 到 Y，这 11 处恢复了哪几处**」的**数字**，而不是简历上多一个技术名词。这是本票唯一的立项理由；出不了数字就据实关票（见 A1）。

## 四、开工前必须先拍板的三个设计决策（不许边写边定）

### 决策 1｜重排插在哪一层 —— 建议：跨查询合并**之后**、节级截断**之前**

即插在 `memory/index.ts:503` 那个 `takenSections` 循环**之前**，对 `ranked`（已去重候选）整体跑一遍。

- **取它的理由**：① 只跑一遍（≤80 对），不是分 4 趟各跑一遍；② T3 的 miss **全部发生在"最终入选"这一步**（`not_topk` / `below_topk` 都是"排在榜尾之外"），插在这里**直接对准靶子**。
- **不取**「每查询出口各跑一遍再合并」：算力 ×4，且合并键是 RRF **累加分**（R1-b），重排分进来还得再造一套合并规则——那是新语义，不是本票该背的。

### 决策 2｜重排**只改序、不改成员**（第一版刻意如此）

距离闸 `MEMORY_MAX_DISTANCE` **原样保留**为池构造侧的前置过滤；重排**不新增、不删除**任何候选。

- 理由一：**可归因**——A/B 的差异纯粹来自排序，不混入"成员集合变化"这个混杂因子。
- 理由二：黄金集 5 条 **negative** 本来就被距离闸挡在池外；**动闸 = 有把负例放进注入集的风险**（A2 就是防这个）。
- ⇒ 这条**可证伪**：若只改序、recall 零变化 ⇒ 本票结论是"重排在现池深下无效"，据实关票。

### 决策 3｜分数落库：**加新列，禁止改老列语义**

- `retrieval_candidates` 现无重排字段。建议新增 `rerank_score REAL` + `rerank_rank INTEGER`（可空 = 未重排行，兼容历史行）。
- ⚠️ **禁止复用 `final_rank`**：本仓已因「同名不同义」栽过两次（`trace_id` ↔ 链锚；R1-b 的 `final_rank` 旧=名次最小 / 新=累加分最大）。重排分是第三个量纲，必须新列。
- DDL 走 `db/index.ts` 的 migrations `ADD COLUMN`（已有 30 行先例，实测 0.10 ms / O(1) / 不重建表）。
- **`RetrievalDroppedReason`（`db/repository/retrievalEvents.ts:40`，封闭集 `'threshold'|'status'|'not_topk'|'budget'|'section_dup'`）要不要加值**：由决策 2 推出**不需要**（只改序不改成员 ⇒ 丢弃语义不变）。但**必须扫全仓消费方**再落锤——本仓纪律「族修必须扫复述文本 + 同规则多处措辞分叉」。

## 六、验收标准（可证伪，逐条要读数）

- **A1｜有效**：同库快照 + 同黄金集 A/B 跑批，给出 T3 那 **11 处的逐条 before/after 名次**与两组 recall 前后值。恢复数 **≥1** 即算有效；**恢复数 = 0 ⇒ 结论是「重排在现池深下无效」，据实关票**——不许靠调池深 / 调阈值凑数（那是别的票）。
- **A2｜负例不劣化（承重）**：negative 组 5 条的**判红数不得上升**（现制 4/5）。这条防的是"召回暴涨稀释精度"。
- **A3｜延迟（必给读数）**：`retrieval_events.retrieval_ms`（列在 `retrievalEvents.ts:146`）的 **p50 / p95** 前后对照。阈值**实施前由用户拍板**（店长建议 p95 增幅 ≤ 50%；检索在回复关键路径上）。⚠️ 「感觉没变慢」不算过。
- **A4｜降级可用**：sidecar 返 503 或被杀后，检索仍返回**非空**的 RRF 序结果；流水能**区分**降级态与正常态。**真空性反对照**：正常态下不得出现降级标记。
- **A5｜尺子自证不破**：跑批 canary（必中 + 必不中条钉在同一锚点）仍 ✅；两条不符即拒出报告的行为不变。
- **A6｜确定性**：同输入连跑两遍，跑批 json 与 md **各自 sha256 全等**（B1 已确立，重排不得引入随机性）。
- **A7｜回归**：`pnpm test` 全绿；`pnpm lint` 过。

## 七、风险与停损

1. **池浅**（每通道 20 / 融合池 20 / 4 趟查询）⇒ 重排能重排的只有这几十条。若 A1 恢复数为 0，**据实关票**，结论写「瓶颈不在这个池的序，在池的成员」。
2. **延迟在关键路径**：每次回复都要检索。S0 的单对延迟读数 × 候选条数 = 预算下限——**S0 就要把这个数报出来**，别等 S4。
3. **与本仓「零新依赖」形态结论的张力**：见 §八。
4. **诊断脚本自证可能再次被打断**：见 §三 末尾的 ⚠️。
