> **状态：已立 · 未派活。** 等点名后开工。本文件只记**已实测**的事实与我已裁的判据方向；实现形态留给派活单。

## 一、为什么有这票

`session/4c8acf70` 首次真实 fan-in 收口（PR #96，merge commit `9497b9b`）暴露出：收口链上的两道机器门禁**都分不清「零新增合并」与「合并里夹带改动」**。

1. **推门禁**（`.push-gate` / `LAST_REVIEWED`）：审查者逐字看的是**猫分支 tip**，推上去的是**fan-in 合并提交** —— 两个不同 sha。门禁只比 sha 字面量 ⇒ 收口方写了一个审查者从未逐字看过的 sha，门禁照放。
2. **交接链**：`handoff-gen` 为这个**内容零新增**的合并自铸锚、生成并投递了一份交接文档 ⇒ 为合并动作白烧一轮审查。

## 三、已裁：零夹带的**正判据** = 双向并集等式

```
hash-object(diff(M^1, M)) == hash-object(diff(base, M^2))
  且
hash-object(diff(M^2, M)) == hash-object(diff(base, M^1))
```

- 两条**都要**：单向只证「没多带」，双向才证「也没少带 / 没被解冲突改写」。
- 取值口径必须写明：`git diff <a> <b> | git hash-object --stdin`。**同一组 diff 换口径就是另一个数**（本仓 D12 立过的规矩：计数/取值必须写明单位）。
- 基线取 `git merge-base`，**不取「收口当时的 dev」** —— 取后者会把两支共有的历史文件误算成引入面（本次实测：取 `c173bae` 得 8 文件，看着像夹带；取 `09e164a` 才是 6 文件）。

| 候选                                        | 否决理由（实测）                                                                                                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`M^{tree} == M^2^{tree}` ⇒ 判零夹带**     | **恒假**。本次 `42ef835…` ≠ `c0b580f…` —— fan-in 的树是两支并集，`^1` 侧的增量也在树里，**真 fan-in 永远不可能等于 `^2` 的树**。把它当门禁 = 一道永不触发的假门 |

## 五、契约（派活时不得擅改）

- 门禁**不得**退化成「只看 sha 字面量」以外的静默放行：新增判据只准**向严**（多拦），不准放松现有 sha 比对。
- 正判据的正负样本必须**成对**给出：一个真 fan-in（应过）+ 一个「合并里塞了一个文件」的构造提交（应拦）。**只给正向样本 = 判据恒真，不算验过。**
- 交接链的抑制判据若落地，必须与 §四 已否决项的实测对照一并写进报告 —— 说明为什么换了这个判据。
