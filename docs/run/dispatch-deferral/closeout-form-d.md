## 六、机制面发现（本轮首次实测）

### 6-1 pre-push 门禁在 worktree 里读**相对路径** `.push-gate` ⇒ 从集成分支 worktree 推送必然被挡

`.husky/pre-push` 的 `GATE_FILE=".push-gate"` 是**相对路径**，解析到**当前 cwd**。收口链的推送动作发生在**集成分支 worktree** 内（`D:/Game/ai/catStudy-sessions/4c8acf70`），那里**没有** `.push-gate`（其在主仓库根）⇒ 实测第一、二次 push 均报「❌ 推送阻断：未找到审查记录」并附 `deliver_pending`（每次都触发一轮交接文档补投）。

**处置**：在 worktree 根另写一份同值 `.push-gate`（`.gitignore:59` 已忽略，不污染 status），push 即过。

**这是收口链的结构性缺口**（与既有记录「收口会话自身 worktree gate 被跳过」同源）：门禁的**判据文件位置**与**推送动作发生地**不同面——判据面取 cwd 相对，执行面在 worktree。**建议立单**：`GATE_FILE` 改从 `git rev-parse --git-common-dir` 派生绝对路径，或推送前由收口流程显式同步两处。

### 6-2 `handoff-gen` 在 pre-push 中被反复调用，且 `CATSTUDY_SESSION_ID` 显式指定会**绕过去重**

同一轮 push 尝试中，`deliver_pending` 每次运行都投递一次交接文档：日志显示「`aabeb27` 已投递过，但 `CATSTUDY_SESSION_ID` 显式指定——按明确意图重新投递」，随后 server 报不可达、重试 2 次、每次**自铸新锚**（三个不同 uuid）⇒ **一次收口动作可产生多份同内容交接投递**。

- **读数**：`handoff-gen` 报 `http://127.0.0.1:3200` 不可达，但**同期我用 MCP 通道查库正常返回** ⇒ server 是否真不可达、还是 `handoff-gen` 自身探针超时，**未定案**（两者判据面不同，不构成矛盾证据）。
- **不阻断收口**：push 的失败原因是 §6-1 的 gate 文件，与投递无关。
