# 票面 · A2A 派发被队列 drain 延迟 —— 症状、取证与待证格

> 立项时间：2026-09-16（本地 12:1x）
> 来源：店长复盘自己 12:01 给 ds猫 的派活单为何没被执行
> 状态：**已立 · 形态已裁（§五-2 = D）**；**根因已定案**（延迟，两例实测 47/68 分钟，见 §三-2 / §三-3）；
> 修复形态已由店长裁定为 **D（两个 await 由串行改并行）**，A/B/C 全落选（理由见 §五-2）

## 结论先行

执行者一轮的收尾若**同时**满足两条：

1. 该轮回复有 A2A 派发目标（@ 了别的猫 / `post_message` 投了靶）；
2. 该执行者**自己的队列非空**（有排队命令待执行）

则第 1 条的派发**被推迟到该 drain 子树整条跑完之后**才发出（最坏实测 **68 分钟**）——**会到，但晚到**。

> 立项时写：「不是丢掉，是被排在 drain 之后……形态上等同丢单」；
> 12:1x 据 12:00–12:16 窗口改判「**丢弃**」；
> **13:0x 决定性读数推翻该改判 —— 是延迟，实测 47 分钟**（§三-2 有逐条取证）。
> 前一次改判的错因不是看错数，是**窗口取早了**：当轮认定「链已解开、末端 = 店长 12:16:02 那轮」不成立，
> 该链此后又跑了 32 分钟（12:18:51 → 12:48:36），迟到的派发行正落在窗外。
> ⇒ **判「丢弃」的取证面不是某个时间窗，而是「外层帧已恢复」**；「窗口内没看见」≠「不会发生」。

## 二、机制（代码读数，标注置信度）

`packages/server/src/execution/serial.ts`：

- `:798` `finalizeRun(...)` 弹队列，命中则 `:813-815` `await drainQueuedCommand(ctx, agent, queuedCmd, claudeRan)`；
- `:830` `if (policy)` 起的 A2A 派发段（`:942` 打 `agent-to-agent dispatch`）**在 drain 之后**；
- `:809-812` 的注释自陈这次次序调整的理由：让队列命令优先，避免它干等当前回复的 A2A 嵌套链（该注释并称 A2A 派发本身是 `await` 的，引用了 d448413a 案例「被两层 A2A await 拖 5.9 分钟」）。

⇒ **机制读数**：drain 内的命令会跑它自己的一整条 A2A 嵌套链（每层 await 下一层），外层帧停在 `:814` 的 await 上；`:830` 的派发于是被排在整条链之后。

**置信度分级**：

- 「两条消息有 mentions 而未派发」= **实测**；
- 「未派发与队列非空 4/4 同现」= **实测相关**（样本 2 对，小）；
- 「因外层帧停在 drain 的 await 上」= 原为**代码读数 + 日志序推断**（`serial.ts:811` 那段注释是**作者自陈**，不是测量）；**§三-2 之后升为实测** —— 派发行的时间戳与它所属执行帧的 `ended_at` 相差 47 分钟，这只能是「帧未恢复」。
- 补一条机制上限：`dispatch()` 本身 await 目标那一轮的执行 ⇒ **延迟随嵌套深度叠加，无固定上界**。47 分钟不是「最坏情况」，是本次链长（73c1a7d7 那条 10 层）下的取值。

## 三、待证格（本票最重要的一格）

2. **V2 反向对照**：修复前同构造 ⇒ 复现「派发行迟到到超出观察窗」（**不是「无该行」** —— §三-2 已证不丢），**先红一次再绿**。反向对照若按「无该行」写，会随链长漂移而假绿。
3. **V3 不回归**：drain 优先的原意不得丢——排队命令仍不得干等 A2A 嵌套链（即 d448413a 那类 5.9 分钟干挂不许回来）。**V1 与 V3 是同一根绳的两端，只满足一端不算修好。**
4. **V4 真仓留痕**：`messages.dispatch_state` 不得出现「mentions 非空、且本轮回复结束已远超阈值，state 仍恒 null」的行。

5. **V5 并发用例（门裁后新增，本笔必做）**：构造「执行者有长跑排队命令 + 同轮有 A2A 目标」⇒ 断言两子树**并发**

## 五、边界

- **不在范围内**：配额与角色白名单（本票已实测排除）；`post_message` 的 route signal 落库（实测正常，`mentions` 列已写入）。
- **不动的**：`finalizeRun` 的 FIFO 语义、`drainQueuedCommand` 自身。
- 形态候选（A：派发不 await drain，先登记后执行；B：把 A2A 派发移出 drain 的前置位；C：给 drain 加超时并把派发挪回前置）——**派活前由店长裁决，不写死在票面**。
- **§三-2 之后新增的硬约束（对三个候选都适用）**：`dispatch()` 自身 await 目标那一轮 ⇒ 单纯「把派发挪到 drain 之前」会把 d448413a 反向触发回来。
  故候选必须回答**「派发登记」与「派发等待」是否解耦**，否则是在两端之间搬同一块石头。
- **不追求「消灭迟到」**：本票要的是**派发时点不随 drain 子树长度漂移**。A2A 链本身跑得久是另一回事，不在本票范围。

### §五-2 形态裁定（店长，2026-09-16 13:1x）：**D —— 两个 await 由串行改并行**

原 A/B/C 三个候选**全部落选**，理由是 §五末那条硬约束已经把它们的共同病根说穿了：
**三个候选都在「drain 先」与「派发先」这两端之间搬同一块石头** —— 搬到哪一端，另一端就吃延迟。

**D 是第三条路：谁都不搬。** 两个子树在**同一帧内本无依赖**，它们的唯一关系是「都在本帧收尾之后」——
把这条串行关系改成并行关系，V1 与 V3 **同时**成立，因为没有谁排在谁后面。

```
现状：finalizeRun → await drain(~47min 子树) → await A2A 派发
形态 D：finalizeRun → ┬─ drain 子树 ─┐
                      └─ A2A 派发   ─┴→ 帧尾合并 await
```

**为什么不是 A（登记/等待解耦）**：D 保留了一条 A 会丢的通道 —— `claudeRan` 冒泡。
`:536` `let claudeRan = needsLock` → `:1038` 子链返回值 `|| claudeRan` → `:1071 return claudeRan` → 顶层
`anyClaude` 判定（决定脏文件清理）。A 把派发登记化 ⇒ 这条返回值无处回传 ⇒ 顶层清理判定漏判。
D 两个 promise 都被 await，**语义逐字保留，只改时序**。

**动什么**（只此一处，`drainQueuedCommand` 另外四个调用点 `:514` / `:635` / `:1102` / `:1714` **一律不动**）：
`packages/server/src/execution/serial.ts` 执行成功收尾段 —— `:813-815` 的 drain、`:1020-1047` 的 A2A 派发、
以及帧尾的 `claudeRan` 合并。

**已知行为变更（须在交接文档记，不许静默）**：并行后 drain 命令的回复与 A2A 目标的回复**落库顺序可能交错**
（现状是 drain 子树全部先于 A2A 目标）。这是本形态的代价，属 UI 观感面，不影响路由正确性。

**已知行为变更 ②（店长门裁时补，同须记）**：两子树**同时派发同一只猫**时，它进该猫 FIFO 的**次序不再确定**
（谁先占槽位不定）。两支都会入队、都会被执行（单槽位零违反，见 ds猫 报告 §二实测），故**不是丢失，只是次序不保证**。

**派活第一道门（只读取证，未答不许动码）** —— 四条并发安全性，任一被推翻即停下报店长：

1. `state.acquireLock/releaseLock`（`:531-532` / `:1113`）确认是**引用计数**而非互斥（店长初核为引用计数，实施者独立复核）；
2. EngineState 的 mention 配额「检查 + 预留」原子段（`:963-967`）在并发下是否仍原子；
3. 两子树并发时 SQLite 写（WAL）与 `bus` 事件序是否可接受；
4. **结构性判据**：drain 命令的 agent 与 A2A 目标 agent **是否恒不同**。
   drain 跑的是**执行者自己**的排队命令，A2A 目标是 `policy.allowed`（别的猫）⇒ 初判恒不同。
   **若这条被推翻（存在同 agent 并发），D 不成立**（违反「每 agent 单槽位 FIFO」）——停下报店长，退形态 A。
