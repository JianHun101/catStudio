## 结论先行

`serial.ts` 执行成功收尾段的两个 `await`（drain 子树 / A2A 派发子树）**由串行改为并发启动 + 帧尾合并 await**。生产面只有一个函数内的时序改动：**语义逐字保留、只改时序**（`claudeRan` 冒泡通道完整）。

三条验收全部拿到读数：**V5 主判据先红后绿**（反向对照精确命中单格）、**V3 非回归绿**、**V4 真仓基线 3/44**。

## 一 · 改了什么

| 落点                                                          | 改动                                                                                                                                                                                              |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/server/src/execution/serial.ts:809-825`             | 原 `if (queuedCmd) { claudeRan = await drainQueuedCommand(...) }` → `const drainP = queuedCmd ? drainQueuedCommand(...) : Promise.resolve(false)`（**并发启动，不 await**）+ `let dispatchP` 声明 |
| `packages/server/src/execution/serial.ts:1050`                | 原 `claudeRan = (await executeAgentsSerialImpl(...)) \|\| claudeRan` → `dispatchP = executeAgentsSerialImpl(...)`（**并发启动，不 await**）                                                       |
| `packages/server/src/execution/serial.ts:1085`                | 帧尾新增 `const [drainedRan, dispatchedRan] = await Promise.all([drainP, dispatchP])`，`return claudeRan \|\| drainedRan \|\| dispatchedRan`                                                      |
| `packages/server/src/execution/serial.test.ts:1714` / `:1764` | 新增 V5 / V3 两格                                                                                                                                                                                 |

**边界遵守**：`drainQueuedCommand` 另外四个调用点（`:514` / `:635` / `:1102` / `:1714`）**逐字未动**；`finalizeRun` FIFO 语义、`drainQueuedCommand` 自身未动；`git-utils.ts` 未动。

**为什么 `claudeRan` 改成帧尾并集**：两条子树各自以**同一个基准值** `claudeRan` 启动，返回值在帧尾 `||` 合并。布尔或运算是可交换的，故与串行下的逐次 `||` 等价；票面 §五-2 弃候选 A 的理由（登记化会让 `claudeRan` 无处回传、顶层 `anyClaude` 脏文件清理判定漏判）在 D 下不成立——两个 promise **都被 await**。

## 三 · 三条已知行为变更（票面 §五-2 已声明，此处逐条落地确认）

## 四 · 本笔新增的边界（票面无，实施时发现）

**失败路径的不对称**：`Promise.all` 下，任一子树抛错 ⇒ 帧**立即**进 catch（与串行同）；但另一子树**不再被帧等待**（串行下如果先抛的是 drain，派发根本不会启动）。两个方向都有变化：

- 先抛 drain：派发**已经启动**（串行下它不会启动）⇒ 一侧是「不再丢派发」，可读作改善；
- 先抛派发：drain 继续 detached 运行到结束。

**安全性**：`Promise.all` 对两个 promise 都挂了处理器，故后续拒绝**不会**产生 `unhandledRejection`；被抛出的那个错误照旧进原 catch 路径（`log.error` → `finalizeRun(success:false)` → 队列 drain 兜底）。**未构造异常对照**——这是声明不是证明，见 §五。
