1. **Phase I 的生产代码会这么写。** 这正是 Phase T / Phase I 存在的理由——本报告只提供实测依据，不构成实现验收。

5. **24 个存量 worktree 的迁移。** D5 已裁不迁移，未验。

## 三、S3 缺口清单

### S3-1【阻断级】`for-each-ref` 裸前缀收不到猫分支

|            | 内容                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------- |
| 原文       | 票面 C1：「按前缀 `session/<sid8>-` 列出猫分支」                                                                |
| 实测       | `refs/heads/session/<sid8>-` **只命中精确同名** `session/<sid8>-`；`-catA`/`-catB` **一条都收不到**             |
| 原因       | git 对不含通配符的 pattern 按 **`/` 边界**匹配，`<sid8>-` 后面直接接 `catA`，不在 `/` 边界上                    |
| 正确写法   | `refs/heads/session/<sid8>-*`（实测命中 3 条）。`git branch --list '<prefix>-*'` 与 `for-each-ref` **实测等价** |
| 危害实证   | 裸前缀 ⇒ 枚举 **0 条** ⇒ 循环体 **执行 0 次** ⇒ **全链零报错**，猫的提交（确实存在）完全不在集成分支上          |
| 与 E5 叠加 | E5 =「集成侧空合并静默成功」，S3-1 =「枚举侧空集静默跳过」⇒ 合成**全链零报错的静默不合并**                      |

**这条为什么最容易漏**：全仓 `for-each-ref` **零命中**（票面已复核），没有既有用法可参照；而失败形态是**静默的**——不报错、不抛异常，只是什么都不做。

### S3-2【实现细节】冲突码不止 `UU`

|          | 内容                                                                                                               |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| 原文     | 票面 C4：「冲突后 `MERGE_HEAD` + `UU` 存在 ⇒ 守卫能探测到」                                                        |
| 实测     | 分叉点上**不存在**的文件被双方各自新增 ⇒ 冲突码 **`AA`**；分叉点**已存在**的文件被两边改 ⇒ **`UU`**。两者可并存    |
| 实测读数 | `status="AA both.txt \| UU shared.txt"`（同一次 merge 内两种码并存）                                               |
| 影响     | 守卫若只查 `UU`，**会漏判「双方各自新增同名文件」形态**                                                            |
| 建议     | 守卫查全码集（`DD/AU/UD/UA/DU/AA/UU`），**或直接只查 `MERGE_HEAD`**——后者实测非恒真（非冲突态 `rev-parse` code=1） |

### S3-5【边界】空后缀分支会被 `<prefix>-*` 命中

`*` 可匹配空串 ⇒ 若存在分支 `session/<sid8>-`（cat8 为空），会被枚举进 fan-in。实测该分支确实被枚举到（`命中=[session/abcd1234-, ...]`）。下游需过滤空 cat8，或保证不产生这种分支。

## 决策留痕

### 为什么每格各起一个一次性仓，而不是一个仓跑到底

格与格之间会互相污染（分支名冲突、worktree 路径占用、`MERGE_HEAD` 残留），且**失败格会把状态带进后续格**，导致后续读数不可信。每格独立仓的代价是多几次 `git init`（毫秒级），换来的是**任何一格可单独复跑、读数不依赖执行顺序**。

### 为什么 A2 是复刻而不是调用生产代码

`ensureSessionWorktree()` 内部走 `getMainRepoRoot()`，在一次性仓的 cwd 下会解析到**本仓**——直接违红线 1。故 A2 逐句复刻其判定骨架并**在脚本内注明复刻来源**（`git-utils.ts:379-433`）。保真度边界见报告开头「覆盖边界自陈」第 2 条。

### 为什么额外做变异验证

票面 S2 要求的三条反向对照是**负向确认**（判据在应当为负时报了负）。但若判据函数本身写错（例如 `pass` 恒 `true`），负向对照也救不了。变异验证是**正向证伪**：故意注入票面原文的错误写法，确认判据真的会红。成本极低（一次 sed + 一次跑），收益是「这批绿不是恒真绿门」有了直接证据。

### 本票与 Phase T / Phase I 的交接

本报告的直接消费者是 **Phase T（仓内测试先行）**：12 格每一格都给出了「命令序列 + 期望读数」，Phase T 可逐格翻译成 vitest 用例。**S3-1 必须先在 Phase T 的判据里固化**，否则 Phase I 照票面字面实现会把静默不合并带进生产。
