4. **冲突 ⇒ 显式停**，复用 `fanInCatBranches:159-171` 的 `conflict`/`recovered` 语义（abort 回可重跑态）；**不静默吞**。

## 五、两处本轮首次出现的机制面发现

### 1. fan-in 合并提交会进交接链（自铸锚 ⇒ 空转审查轮）

`pre-push` 的 `deliver_pending()` 走 `handoff-gen.mjs --gate-deliver`（pending 队列 + **兜底 HEAD**）。fan-in 的 `--no-ff` 合并提交**没有 `catstudy [uuid]` 标记**（`commit-msg` 钩子对 merge 明确「放行」），于是 handoff-gen **自铸锚**并投递了一份交接文档：

```
[handoff-gen] 无源链锚（commit message 无 catstudy [uuid]）——自铸锚 01c1bdb2-…
[handoff-gen] ✅ 交接文档已投递 … → @吐槽猫 审查
```

**后果**：为一个**内容零新增**的机械合并生成了一份交接文档 + 一轮审查请求。本轮实测到的副作用是：11:56:49 一条消息投递并排队给了店长。

**这是 Phase I 引入的新面**（此前会话分支上没有本地 no-ff 合并提交）。**未立单，记账待裁**——它不产生错误结论（合并内容已被审），但产生空转轮次，且与记忆里既有的「自唤醒回环」同族。

### 2. pre-push 门禁的 `LAST_REVIEWED` 语义（据实声明，不粉饰）

门禁判据是 `LAST_REVIEWED =本地推送 sha`（`.husky/pre-push` 判据①）。本轮：

- 审查者审的是**两条猫分支的 tip**（`6f22b52` / `1225e1d`）；
- 推的是**fan-in 之后的会话分支 tip**（`f375879`），它是两个已审 tip 的**直系后代**；
- 故 `.push-gate` 被写成 `f375879`——**一个审查者从未逐字看过的 sha**。

**我认为这在本轮是对的，理由是可验证的**：两个已审 tip 都是 `f375879` 的直接祖先，且两笔合并的内容差分（562+/4- 与 546+/40-）**在合并前后逐字节一致**（§一可加性核对）。即：**当且仅当 fan-in 是内容零新增的机械合并时**，把门禁写成 fan-in tip 等价于写成两个已审 tip 的并集。

**但这是判据语义的一次外延，且靠收口方自律**：门禁本身分不清「内容零新增的合并」与「在合并里夹带改动」。**建议立单**（见 §七-3），在那之前，收口记录必须逐笔写明合并的内容差分——本条即是。

## 八、留一句给将来的读者

本轮是「结构」第一次真正跑起来的一轮，也是「结构刚跑起来就暴露了下一层缺口」的一轮：

- Phase I 隔离了 **git 树**（三猫各树各分支，本轮实证），**没隔离 `os.tmpdir()`** ——两猫并发跑同一个测试文件会写同一批物理路径，把提交口变随机红。**隔离是有边界的，边界要一层层找**，不是一次接线就完事。
- 同一个「工作树共享 object store」的性质，既是 `serial.ts:770` 被**证伪**为缺口的原因（猫分支的 sha 在会话树里读得到），也正是 G 方案**成立**的原因。**同一个机制面既能解除一个担忧，也能支撑另一个方案——判据要落在具体读数上，不落在机制名上。**
