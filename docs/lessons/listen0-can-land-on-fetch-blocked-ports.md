# `listen(0)` 可能落到 Fetch 的禁用端口上——服务真的在监听，`fetch` 却在发请求前就拒

## 撞出来的场景

一条 pre-commit 里的测试偶发红，签名是 `Test timed out in 10000ms.`，位置在**重试有界**那条用例上。
偶发意味着难复现：先怀疑 keep-alive 僵尸 socket（试过 `Connection: close`，**不治**，
异常照旧 5 次），再排除 Windows 保留端口段与负载成因（空闲态同样复现）。

探针读数把方向钉死：`detail = fetch failed`、`elapsed` 稳定在 **30.0–30.2s**、
`healthCount = 0`——`/health` 一个请求都没到过 stub，**服务没收到，不是服务慢**。

## 现象

- **服务真的在监听**：裸 TCP `CONNECT-OK`、`listening: true`。
- 但 `fetch` 在**发请求之前**就被拒，`cause = "bad port"`——**连 TCP 都不建，且永不恢复**。
- 对照（正常失败）：`cause = "ECONNREFUSED"`——端口无服务、快速失败、**可恢复**。
- 撞上后重试路径吃满 `PROBE_TIMEOUT_MS = 30_000`，撞穿 harness 预算 ⇒ `Test timed out`。
- 实测命中的端口（15 个）：`1719` / `1720` / `1723` / `3659` / `4045` / `4190` / `5060` /
  `6000` / `6566` / `6665`–`6669` / `10080`。
- **对照组证明判据非恒真**：同为「无服务端口」，黑名单外的 `49152` / `50000` / `51234` /
  `65530` 全部返回 `ECONNREFUSED`，只有黑名单内的返回 `bad port`。

## 机制

`listen(0)` 让 OS 随机分配端口，**偶尔**落到 WHATWG Fetch 规范的禁用端口黑名单里。
命中率实测 ≈ **15 / 13977 ≈ 0.1% / 次分配**——这不是时序竞态，是端口分配的**确定性缺陷**，
只是触发取决于 OS 恰好分到什么端口，所以表现为「偶发」。

它最先打红**重试路径**的用例，是因为那些用例用**模块默认预算**（30s），而 harness 预算当时更小 ⇒
默认预算 ≥ 框架预算，一次异常就撞穿。

## 正解

- **判据不能抄黑名单**：那份表**随 undici 版本漂移**，抄一份等于把同一个 bug 换成
  「下次静默复发」；且 **TCP 层判不出来**（实测同一端口 `CONNECT-OK` 与 `bad port` 并存）
  ⇒ **`fetch` 是唯一 oracle**。正确判据 = **真的 fetch 一次**（仓内辅助函数 `isFetchReachable`，
  与 `listenFetchable` / `withFetchablePort` 同在 `packages/server/src/test-helpers.ts`）。
- **生产侧 pin 态：启动即报错，不静默换端口**——客户端按固定端口对接，换了就是骗人。
  实测对照：显式端口落在黑名单时，改前是「静默起来、主进程永久连不上」，改后是「**启动即抛错**」。

## 可复用的动作

1. **概率性根因下，回归跑几乎不构成证据**：实测检出率「单文件 × 20 ≈ 2%」「全量 × 3 ≈ 0.3%」。
   全绿只证明「没引入新问题」，**证不了修复有效**。
2. **承重证据只能是把偶发变确定性的注入对照（变异）**：
   - 把校验函数的 `catch` 改成 `return true`（模拟「校验写了但没用」）⇒ 判别力用例必红；
   - 强制绑一个黑名单端口并旁路校验 ⇒ 原 `Test timed out` 签名被**确定性复现**。
3. **探针语义宁可放宽**：`isFetchReachable` 判「任何 fetch 失败 ⇒ 不可达」，不比对错误串——
   零版本漂移，代价是极罕见的 localhost 抖动会触发一次无谓换端口。
4. **定位轮要在票面写明收敛条件**：这次定位轮撞了 30min 硬超时，根因是「机制分析没收敛边界」——
   一路写了 8 个探针，最后一个去扫全端口段拿「权威黑名单」时卡死。
   而**权威黑名单对修复并不必要**；「拿到 `err.cause` 即停」本该事先写死。
