# 比对审查分支与 dev 求差异：diff 归零 ≠ 无冲突——基线若包含被测提交，这个判据恒真

## 撞出来的场景

2026-09-22 收口「文档与注释里的行号锚去行号化」票时，剩下的 4 处合并冲突
（`AGENTS.md` / ADR 0014 / `map.md` / 一份票面）到底是什么性质，店长与审查者各执一词。

审查者取了一条比对基线，算出「两侧逐字节相同」，据此写下一句结论：**原叙事不成立**——
即「那 4 处冲突是真冲突」这个说法是错的。店长复核后发现：**那条基线是审查分支尖端，
而审查分支本来就包含待审提交**。拿一个「包含 B 的 A」去和 B 比，差异必然为零。

## 现象

- 判据**恒真**：不管被比的两侧真有差异还是真没差异，只要基线选得不对，读数都是「相同」
- 不报错、不告警：`git diff` 老老实实返回空输出，退出码 0
- 结论**方向反了**：本来要证「有冲突」，读出来的是「无冲突」，于是把原本成立的叙事判成假的

## 机制

比对 A 与 B 求差异，前提是 **A 与 B 互不包含**。若 A ⊇ B，则 `diff(A, B)` 必为空——
这跟 B 本身长什么样无关。

用「审查分支尖端」当基线是这类错误的高发形态：审查分支是**从待审提交长出来的**，
天然包含被审对象。它看起来是个合理的「另一侧」（毕竟是另一个分支），实际是超集。

## 可复用的动作

给「两侧比对」类判据加一条**前置证明**，并把证明写进结论里：

> 比对前先证 A 与 B 互不包含（`git merge-base --is-ancestor B A` 为假 **且**
> `--is-ancestor A B` 为假）；证不出互不包含，这次 diff 不作数。

配套的直觉检查：**「把被比的对象换成一个任意值，这个判据还会给同样的读数吗？」**
会 ⇒ 它测的不是被测对象，是基线。

## 更一般的形态

**恒真门**：判据在「有问题」和「没问题」两种输入下给同一个读数。
它的兄弟形态在本仓反复出现——验收用例在旧实现下也能过
（见 [新写的验收用例必须在旧实现下必红](red-test-must-fail-under-old-implementation.md)）、
验收指标在被测区间分不开档、断言断的是默认值而非实际生效值
（见 [断 env 看回落默认值不算数](env-default-assertion-is-coincidence.md)）。

共同点：**门是绿的，但门后面没有东西。**
