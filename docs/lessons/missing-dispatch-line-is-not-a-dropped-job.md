# 没看到派发行 ≠ 派活掉单——重投前先查 execution_logs 里有没有还在 running 的祖先执行

## 撞出来的场景

派发延迟票（`dispatch-deferral`）记录了一次实测：给某只猫的派活**迟到 47 分钟才送达**。
调度方当时看到「上一轮的派发行还没出现」，据此判定**丢弃**，于是重新派发了一次；
猫按第二次派发把活做完了。随后**第一次派发也到了** ⇒ 同一张票被投了两遍。

同票的第二例更极端：一条**审查回执**迟到送达时，回执里的内容**早已被处理完**
（它指向的那个提交已经是 `dev` 的祖先，随带的几条 OQ 也都裁完了）。
在接收侧，这看起来就是一次莫名其妙的重复派发。实测代价 = 一次空转执行、零错误动作。

## 现象

- 「触发我的消息」没出现，有两种截然不同的成因：**没发出去**（真丢）和**发出去了但延迟到达**（迟到）
- 只看「没看到派发行」，这两种分不开
- 而两者的**正确动作相反**：真丢 ⇒ 该重投；迟到 ⇒ 重投就制造重复派发

## 机制

派发链路上「消息已落库」与「消息已抵达消费方」是两件事。中间隔着队列、槽位等待、
上下文注入、执行调度多层缓冲。**观测点选在链路末端**（消费方看不到行）时，
上游的任何延迟都表现为「没有」。

**「没有观测到」与「没有发生」不是一回事**——这是本条的根。

## 可复用的动作

**收到任何「触发我的消息」时先做两步（本仓现行口径）**：

1. **算时差**：取该消息的 `created_at`，与自己这次执行的 `started_at` 相减。
   差值大 ⇒ 按「**迟到，内容可能已作废**」处理，**不要直接开工**。
2. **核内容落点**：这条消息要求的东西是不是已经完成了——
   它指的提交是否已在 `dev` 里（`git merge-base --is-ancestor`）、
   它带来的 OQ 是否已有裁决、它要改的文件是否已经改过。
   **有落点 ⇒ 判重复派发**：不重做、不重启审查循环。

**重投之前**：确认这条链路的**外层执行帧**（同一 `task_id` 的那次执行记录）是否还在
`execution_logs` 里处于 `running`。**还在跑 ⇒ 不是掉单**，重投等于制造重复。

**派发方侧**：重投前先确认外层帧是否还在，否则同样是在制造重复派发。

## 更一般的形态

凡「没看到 X ⇒ 判定 Y」的推理，先问：**我的观测点在哪一层？上游还有谁在缓冲？**
同类形态：`exit 0` 不等于东西进去了（见
[命令 exit 0 ≠ 提交落到了 dev](exit-zero-does-not-prove-content-landed.md)）——
两条都是把「我这侧的命令/观测完成了」误当成「对方那侧收到了」。
