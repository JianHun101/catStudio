# 把外部判据套到本仓前先做适用性映射——判据的射程写在它自己的自述里

## 撞出来的场景

引入一份外部的「设计品味」判据（技能正文）来诊断本仓页面。第一反应是拿判据清单逐条对照、
命中即整改。真做下来会发现：判据里大量条目**本仓根本不在场**（它默认 React/Next、Tailwind、
动画库，本仓是 Vue3 + 手写 CSS），还有一些**字面命中但本意不适用**。

不做这一步的后果不是「整改多了」，是**把判据的射程当成自己的射程**——照单整改会造出一批
为判据服务、不为产品服务的改动。

## 正解：三栏映射表

1. **可迁移 ⇒ 据以诊断**：保留判据内核，并写明「为何可迁移到本页」。
2. **技术栈 / 页面类型不在场 ⇒ 显式标 N/A**：逐条给**排除理由**（例：判据要的状态原语与图标库
   一个都不在场；判据管 Core Web Vitals 而这是内部工具页、无外链图片）。
3. **字面命中但判据本意不适用 ⇒ 显式豁免，不是整改项**：三段式——判据 / 字面命中 / 为何不整改。
   （例：某禁令打的是英文营销文案里当修辞拐杖的破折号，而本仓那个符号是**「无数据」占位符**、
   是显式设计——「我不知道」≠「我没有」。另一例：判据打「每段标题上方的小标签」，
   而本仓那批 `text-transform: uppercase` 是表单字段标签，且内容是中文、`uppercase` 对 CJK
   是空操作——那是「死声明」问题，不是判据所说的问题。）

**总纲：只保留可迁移判据，不适用的显式标 N/A，不硬套。**

**豁免面里若混着真问题，必须单独立项**——不能拿「判据本意不适用」把真缺陷一起豁免掉。

## 射程自述是判据的一部分

外部判据的第一段常常就是它的排除语（例：「Landing pages, portfolios, and redesigns.
Not dashboards, not data tables, not multi-step product UI.」）——而本仓要诊断的页面
**恰是被它排除的那一类**。有的判据另有独立的 OUT OF SCOPE 小节（例：把
「Realtime collab UIs (presence, cursors)」排除，而本仓有流式回复、在线状态、socket 实时推送）。

⇒ **套用前先读它排除了什么**；命中被排除类目时，该判据的结论**降权采信**，
并在报告里自陈这句自述，让读者知道边界在哪。

## 与「外部工具形态选型清单」（ADR 0007）的分工

两者都是**外部来源进本仓前的把关**，但把关对象不同：

- ADR 0007 管**工具形态选型**的流程闸——能力对账前置 / 假设标红 + 实测对称 / 简单形态默认 /
  决策留痕；
- 本条管**判据适用性**——判据射程 vs 在场的页面类型与技术栈。
- 共同点：都要求把「已知事实」与「不适用 / 未验证」**分列留痕**，不混成一句结论。

不重复：0007 不覆盖「判据射程」，本条不覆盖「形态选型」。

## 可复用的动作

1. 引入任何外部判据（技能 / 清单 / 标准 / 成熟度模型）前，先建**三栏映射表**再谈整改。
2. **N/A 与豁免都要写理由**，理由要能被第三方复核（哪条判据、本仓什么不在场 / 为何本意不符）。
3. **报告自陈射程原句**，并写明「本页恰是被排除的类目 ⇒ 涉及该语义的结论降权采信」。
4. **豁免与诊断分账**：豁免面里藏真问题就单独立项，别让它跟着豁免一起消失。
