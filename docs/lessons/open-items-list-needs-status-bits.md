# 未闭项清单只增不减，会让「零未闭项才删」这条判据不可判——每条要带 [闭]/[开] 状态位

## 撞出来的场景

2026-09-2x 盘点 `docs/run/**` 下 19 个票目录时，最费时的部分不是读内容，是**判断一条
「观察项」到底闭没闭**。清单本身说不了话，只能逐条回到代码/提交里去重核。

盘点实测到同一形态至少两处：

- 提交 UUID 门禁那张票里，一条**已闭**的观察项（`.husky/pre-commit` 已 `unset GIT_DIR`）
  仍被列在「两条未闭观察项」里；
- 测试环境变量污染那张票里，一条**自标「已收口」**的观察项，仍被列在同一份
  「未闭观察项如下」清单内。

## 现象

清单的初始语义是「**未**闭项」。但没有人负责在条目闭合时把它移出或标闭，
语义就漂移成「曾经存在过的项」。

- 后果不是「多读几行」，是**这个清单失去了作为判据的能力**
- 最重的一层：目录删除的判据是「**零未闭项才删**」——清单一旦失真，这条判据**不可判**
  （你永远读不出「零」是真空还是没维护）

## 机制

清单是**只增不减**的，而它承载的谓词（「未闭」）是**状态相关**的。
两者不匹配时，读者无法从「有没有列」推断「闭没闭」，只能逐条重核 ——
于是清单从「省时间的索引」退化成了「额外的核实工作量」。

## 可复用的动作

- 条目标**状态位**：`[闭]` / `[开]`；或把已闭项移出「未闭」节（移到「已闭」节或直接删）。
- **通则**：凡「清单驱动决策」的地方（未闭项 / 待办 / 挂账观察项 / 未覆盖面），
  先回答一句：**什么动作会把一条从这份清单里拿掉？**
  - 答得出 ⇒ 把那个动作写进清单的维护规则，并让状态位可见
  - 答不出 ⇒ 这份清单只会单调膨胀，它的判据会随时间长歪
- 配套：判据里凡出现「零 X」「没有 X」「全部 X」这类**否定式全域断言**，
  要先证「这份清单本身可信」（见
  [全域断言必须把判据口径一起写出来](global-claims-need-explicit-scope.md)）。
