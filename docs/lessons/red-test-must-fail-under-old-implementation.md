# 新写的验收用例必须在旧实现下必红——「我构造了一个场景」不等于「这个场景判得出差异」

## 撞出来的场景

2026-09-14，混合检索票（把「每查询取多少候选」与「最终注入几片」两个语义拆开）写第一条验收用例。
第一版用 `MEMORY_TOP_K=8` 构造场景，跑出来**改动前也是绿的**——这条用例一个字节都没测到本票的改动。

根因：旧实现把同一个数**同时**当「每查询池」与「最终注入数」。当
`MEMORY_TOP_K` ≥ 库内片数时，两趟查询各自都拿全了，池扩不扩根本看不出。
场景是构造了，但它没有**判别力**。

## 现象

- 用例绿了，但绿的原因和被测改动无关
- 换成旧实现重跑，**仍然是绿的** —— 这就是判据没有判别力的直接证据
- 若不回头验旧实现，这条用例会一直留在套件里，提供虚假的安全感

## 机制

一条验收用例的判别力 = **它在「改了」与「没改」两种实现下读数不同的能力**。
`改动前也绿` 意味着两种实现给同一读数 ⇒ 判别力为零。

「构造了一个场景」是**过程**（我造了输入、我跑了）；「这个场景在旧实现下必然不同」是**判据**。
过程做完了不等于判据成立。

## 正解

重做为 `MEMORY_TOP_K=2` 的**必红构造**：此时池大小真正成为约束，旧实现拿不全 ⇒ 必红。

## 可复用的动作

1. **写完一条验收用例，必须拿旧实现跑一次，确认它红。**
   没红过 ⇒ 你不知道它守的是哪条分支，它可能是恒真门。
2. **把红的形态记下来**：哪条断言红、报什么值。这条记录是「判据活着」的证据。
3. **定向回退优于整体回退**：只回退被测的那一条分支（例如只删掉 tie-break 排序），
   确认该用例**单独**转红、其余仍绿 —— 这能把「本用例守的确实是这条分支」
   与「回退整个面」的粗粒度证据分开。
4. **「不变性」守卫本就该在两版都过**：确定性、注入片数、未涉及的输出不变 ——
   这些是**不变性断言**，两版皆绿是正确行为。把「不变」写成「会红」才是假绿门。
   区分标准：这条用例守的是**本票改动的行为**，还是**不该被本票改变的行为**？

## 更一般的形态

**验证面必须与被判面同面。** 判别力来自「两种实现读数不同」，不来自「我跑通了一个场景」。
同族：判据恒真（见 [diff 归零不等于无冲突](diff-zero-does-not-mean-no-conflict.md)）、
断的是默认值而非实际生效值（见
[断 env 看回落默认值不算数](env-default-assertion-is-coincidence.md)）。
