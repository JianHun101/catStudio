# 审查分支上解冲突留下的合并记录，是下一轮合并的冲突源——审查分支必须是纯内容快照

## 撞出来的场景

2026-09-17 前后，「数据库结构治理 P0」这批票的审查链连续撞了三次墙，前两次是基线陈旧，
第三次的根因不同：**同一个冲突被解了两遍**。

- 店长在审查分支上手工解了一次（`734d302`）
- 同一张票的实施猫在自己分支上独立解了一次（`bbc7a8e`）

两份「解过的记录」**互为非祖先**——各自都基于不同的起点，各自都改了同一处。
第三次合并时它们必然再撞一次，而且撞的正是「两份已经解过一遍的同一件事」。
收场是把审查分支 `git reset --hard` 归零（`0cc6b72`）重来。

## 现象

- 解冲突这个动作**看起来是收敛的**（冲突没了，测试绿了），实际制造了一个新的分叉点
- 下一次合并报的冲突，内容与上一次**几乎相同**——读的人会以为「冲突没解干净，重解一遍」，
  于是再解一次，再制造一份「解过的记录」
- 每解一轮就多一份对撞物，审查链可以无限打转

## 机制

**审查分支的角色是「待审内容的一份快照」，不是一条开发线。**

在快照上解冲突 = 让快照长出一段**新的提交历史**。而这段历史在别处（实施猫自己的分支）也会
被独立地长出一份，两份互不包含 ⇒ git 的合并判据必然认为它们冲突。

关键区别：合并**内容**是幂等的（同样的最终树不会冲突），合并**历史**不是。
一旦「解过的记录」本身成了待合并对象，幂等性就没了。

## 可复用的动作

- 审查分支只接受两种操作：`git reset --hard <被审 sha>`，或纯内容级别的覆盖式写入。
  **不接受 merge commit 落在审查分支上。**
- 解冲突的产物落在**开发线**上（或收口那一笔），不落在审查分支上。
- 判「审查分支干净不干净」的判据：**它是不是一份纯内容快照** ——
  即它的树 == 被审 sha 的树，且没有多出任何「为了合并而解冲突」的提交。
- 收口时按**已审 sha 字面量**合，不按分支名合（分支名会在执行那一刻才解析，
  中途别的猫提交会被连带吞进去）。

## 更一般的形态

**「把过程产物留在快照上」会在下一次比对时变成新输入。**
同类：往被当成「基线」的东西里写东西（见
[diff 归零不等于无冲突](diff-zero-does-not-mean-no-conflict.md)）——
两者都违反「对照物必须是常量」这个前提。
