# 执行收尾段：队列 drain 与 A2A 派发并发（execution-tail-concurrency）

> **定稿规格**（2026-09-30 写入）。源活：票 `dispatch-deferral`（PR #98，2026-09-16 收口）；取证两段见源票的 `report-gate-concurrency` / `report-implement-form-d`（已随 `docs/run/` 清理，过程留痕在 git 历史）。
> 本文是「执行成功收尾段的两个子树怎么跑」的**唯一成文定义**，含**三条当契约的行为变更**——改这条链前先读 §4。

## 1. 一句话

一轮执行成功收尾时，**队列 drain 子树**与 **A2A 派发子树**从「串行、互为前置」改为**并发启动 + 帧尾合并 await**：两个子树各自以同一个基准值启动，帧尾用 `Promise.all` 收口。语义逐字保留、**只改时序**。

## 2. 它治的是什么

**症状**：执行者一轮的收尾若**同时**满足两条——① 该轮回复有 A2A 派发目标（@ 了别的猫 / `post_message` 投了靶）；② 该执行者**自己的队列非空**——则①的派发**被推迟到 drain 子树整条跑完之后**才发出。

**形态是「会到，但晚到」**，不是丢单。实测两例迟到 **47 分钟 / 68 分钟**（派发行的时间戳与其所属执行帧的 `ended_at` 相差即该量级）；机制上限是**无固定上界**——`dispatch()` 本身 await 目标那一轮执行，延迟随 A2A 嵌套深度叠加，47 分钟只是其中一条 10 层链下的取值。

**一处取证教训**（值钱的是判据本身）：该缺陷一度被判为「丢弃」，错因不是看错数，是**窗口取早了**——判「丢弃」的取证面不是某个时间窗，而是「**外层帧已恢复**」；「窗口内没看见」≠「不会发生」。

## 3. 形态

| 落点（`packages/server/src/execution/serial.ts`） | 改动                                                                                                                  |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 收尾段 drain 处                                   | `if (queuedCmd) { claudeRan = await drainQueuedCommand(...) }` → 并发启动、**不 await**（无排队命令时为已决 promise） |
| 收尾段 A2A 处                                     | `claudeRan = (await executeAgentsSerialImpl(...)) \|\| claudeRan` → 并发启动、**不 await**                            |
| 帧尾                                              | 新增 `await Promise.all([drainP, dispatchP])`，返回值三者取并集                                                       |

- **`claudeRan` 改成帧尾并集**：两条子树各自以**同一个基准值**启动，布尔或在帧尾合并——或运算可交换，故与串行下的逐次 `||` 等价。**两个 promise 都被 await**（这是「登记化」等替代形态落选的理由：登记化会让该值无处回传，顶层清理判定漏判）。
- **边界**：`drainQueuedCommand` 的其余调用点、`finalizeRun` 的 FIFO 语义、`drainQueuedCommand` 自身、`git-utils.ts` 全部未动。
- **判别格只有一格**：`serial.test.ts` 的「形态 D」用例（闸门挂住 drain、观察 A2A 目标是否在闸门放行前启动）。反向对照（`git restore` 回串行实现）**恰好只红这一格**——另一格（闸门挂 A2A 目标、观察排队命令）在串行/并发下**都绿**，它是非回归守卫、不是判别格。**反向对照若两格同红，说明判据写错了对象。**
- **单测口径的边界**：票面原写「30s 内被派发」，但单测里 `chatStream` 是 mock、时间尺度失真，**墙钟口径在单测层不成立**。单测取的是结构性等价形（派发时点不随 drain 子树长度漂移，强形式 = drain 被无限期挂住时派发照样发生）；墙钟口径由真仓读数承担（见 §5）。

## 4. 三条**当契约**的行为变更（改这条链前先认账）

1. **两子树回复落库顺序可能交错**（原：drain 子树全部先于 A2A 目标）。属 UI 观感面，**不影响路由正确性**。
2. **同目标猫进 FIFO 的次序不再确定**（谁先占槽位不定）。两支都会入队、都会被执行（单槽位零违反）——**不是丢失**。
3. **配额末位竞争由确定转不确定**：仅在名额**将好耗尽**时改变「哪只猫被拦」，**不改「有没有被拦」**；该路径本就有 `warn` + 收发双方提示。

另有一条**退化形态**：并发令牌上限为 1 时，本形态**退化为串行**（回落现状）——非回归、非错误。本部署运行时真值 > 1，故并发无条件生效。

## 5. 已知边界与挂账（引用本规格前先读）

- **未闭验收项：真仓复测**。判据 = `messages.dispatch_state` 不得出现「`mentions` 非空、且本轮回复结束已远超阈值、`state` 仍恒 null」的行，**且判据带时点**（单看 `state = null` 不构成判据）。修复前基线（近 5 小时窗口）：`mentions` 非空回复 44 条中 3 条为 NULL（6.8%），其中两条目标猫**创建时空闲**、此后又执行 12 / 16 次而派发未发生。**取数须在重启后、修复生效的真窗口上做**；取数前不得声称本格已验。
- **因果链未定案**：那三条未取到帧级证据，「成因 = drain 串行」是**形态吻合**；两条替代解释（配额 / 角色白名单拦截、目标名未解析成可路由 agent）**未被排除**。
- **失败路径的不对称未跑对照**（属代码读数，不是实测）：`Promise.all` 下任一子树抛错 ⇒ 帧**立即**进 catch（与串行同），但另一子树**不再被帧等待**。两个方向都有变化——先抛的是 drain ⇒ 派发**已经启动**（串行下它不会启动，一侧可读作改善）；先抛的是派发 ⇒ drain 继续 detached 运行到结束。安全性上，`Promise.all` 对两个 promise 都挂了处理器，后续拒绝**不会**产生 `unhandledRejection`。**真实长链（47 / 68 分钟量级）下 detached 子树与 `finally { releaseLock() }`、catch 里第二次 `finalizeRun` 的交互没有实测。**
- **一处既有注释与实现脱钩已就地更正**：收尾段上方的函数头约束清单原写「A2A 递归与队列 drain 保持原语义，**天然串行**」——正是本规格推翻的前提，已改。
- **一处报备未改**：某连接器测试里 `parseMentionsFromReply` 的 mock 次序注释写「第一次 parse 是 drain 回复」，而生产侧该函数的唯一调用点在 `finalizeRun` **之前** ⇒ 实际次序相反。该用例终态断言两种次序下都成立（故绿），但**不是按标题说的那条路径绿的**；属既有问题、非本规格引入。
