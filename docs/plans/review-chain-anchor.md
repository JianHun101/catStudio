# 审查链锚统一 + 提交钩子兜底化（spec）

> 写者：店长 · 日期：2026-09-10 · 状态：spec-gate PASS（含 `chainRole` 对账位，见 D11）
> 上游：本会话 grilling（2026-09-10 用户拍板）+ ds猫 只读调查单（链锚四消费方口径分歧实测）
> 落点依据：`CONTEXT.md`「文档位置约定」——to-spec 产物落 `docs/plans/`（定稿规格）

## 一、问题陈述

从店长与猫的视角看，症状是一句话：**同一条议题的返工，每次都开出一条新的审查链。**

后果三条，按痛感排序：

1. 并行单被重复提醒淹没——店长的收口队列里同一件事出现七八次，分不清哪条是活的；
2. 审查猫重复读同一份代码、重复给同一批意见，审查轮次与 LLM 消耗成倍放大；
3. 评估与收口错乱（见下），而且**不报错**。

用户原话："每次 commit 文件修改会自动触发 commit hook，但是当实施猫和吐槽猫在返工的时候，会继续触发 commit hook，导致开启多个审查链。严重影响审查链速度以及无效消耗。……需要去掉 commit hook 这个机制，只作为兜底。"

### 根因（已实测，非推测）

痛点的表象是"commit 太多"，根因是 **`commit` 被硬绑成了"投递信号"**，且**"链"在系统里没有唯一权威定义**——四个消费方各持一个近似值，首轮四值恰好相等故长期隐形，返工起全部分歧、同时静默出错：

| 消费方                | 现用口径                                     | 返工后                             | 症状                                                                              |
| --------------------- | -------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------- |
| 提交钩子（投递审查）  | 本轮执行的 `trace_id`                        | 新值                               | **每条返工开一条新链**（叠链根因）                                                |
| 评估归档              | 链末执行的 `trace_id`                        | 该值在消息表 0 行                  | 判词查空 → 判 `success`，**打回检测静默失效**                                     |
| 收口推进              | 判词消息的 `task_id` 反查 commit（假设 1:1） | 一 `trace_id` 名下挂 2~3 个 commit | 取到**错的 sha**；且按 (会话, sha) exactly-once 记账 → **真提醒永久不投且不报错** |
| 重放跳过 / 上下文回捞 | `task_id` 宽查、无边界                       | 一条链 20 条消息 / 跨 5 小时       | 误判"已执行"、把 7.7 万字符历史灌进上下文                                         |

首轮为什么没露馅：触发消息无锚时表达式 `triggerMsg.taskId || traceId` 兜底成本轮 `trace_id`，于是"链锚"与"本轮"恰好同值。返工轮的触发消息带的是**继承值**，与新一轮 `trace_id` 永久分歧。

### 一个时序事实（决定了兜底放哪）

**投递的载体是执行回复（或执行中注入的消息），而 `commit` 发生在回复落库之前。** 因此在 `commit` 那一刻，"这次执行投递审查请求了没有"这个问题**在物理上还没有答案**——提交钩子再聪明也判不出来。这是本 spec 与上一轮口述方案唯一的实质修正（见决策留痕 D4）。

## 二、方案

一句话：**把"链"从约定升级为不变量。**

锚沿用 `messages.task_id`（**不新增列、不造新词**），语义正式收敛为「本条消息所属审查链的首轮标识」；链路每一跳强制携带（首轮由入库时显式写入）；审查类投递另带 `chainRole` 对账位；四个消费方统一按锚查；提交钩子从"投递者"降级为"标记者"，兜底判定移到**执行收尾侧**。

四块：

- **A 链锚域**：锚的产生与继承规则、必填门槛、链内角色对账、四消费方对齐；
- **B 投递与兜底**：钩子降级、兜底移位到执行收尾；
- **C 审查流程升级**：`request-review` 技能（含前置门槛）+ 判词三档；
- **D 文案对齐**：铁律 / quality-gate / system prompt 里"自动触发"的表述全部改写。

## 四、实施决策

### A 链锚域

**A1 锚的定义与取值。** 锚 = 本条链**首轮任务**的 `task_id`，字段沿用 `messages.task_id`。**首轮锚在消息入库时显式写入**：入口早就生成了那个值并把它交给了本轮执行，只是没写回这一列——`connectors/ingest.ts` 里 `traceId = uuid()`（`贯穿全链路的请求追踪 ID`）与 `executeAgentsSerial(..., traceId)` 同值，而 `insertUserMessage` 落的是调用方传入的 `taskId || null`。改为一处 `taskId || traceId` 即可：**不是新造值，是把已有的值落对列**。**不新增列、不新增字段、不引入 `chainId` 别名**——判词域本来就按 `messages.task_id` 查询，值一直存在，缺的只是"哪一轮的值"这个口径。

**A2 生成与继承（显式生成，兜底职责取消）。** A1 落地后，链内每一跳的触发消息在入库时就已带锚，于是 `triggerMsg.taskId || traceId` 中的 **`|| traceId` 支对链内跳永不触发**，只服务真链首轮：

- 触发消息 `task_id` **为空** = 真链首轮（唯一合法情形）→ 取本轮 `trace_id` 作锚；
- 触发消息 `task_id` **非空** = 链内跳 → **原样继承**，绝不用本轮 `trace_id` 覆盖。

`|| traceId` 的**语义降级**（不是删除）：它从"哪一跳漏带就静默开新链的逃生舱"变回"首轮锚生成"。逃生舱之所以能关掉，是因为 A3 主闸把 agent 发起消息的空锚堵在了入口。现状的问题从来不是这个表达式写错了，是**没有任何地方保证链内跳一定带锚**。

**A3 必填门槛（主闸 + 次闸）。**

- **主闸（机械，零 LLM 成本）**：投递入口对**agent 发起的消息**强制要求锚，缺 → 400 拒绝，错误体说明"缺链锚，请带 `task_id` 重投"。用户/前端发起的消息不受此限（它们天然是链首轮，允许空锚）。
  - ⚠️ 待核（标红，不拍板）：入口能否稳定识别"agent 发起"。若有现成的 agent 身份字段可直接判；若拿不到，退化为「消息 mentions 含 agent 时必填」。
- **次闸（语义，最后一道）**：审查猫收到**绕过入口的直投**审查请求且无锚 → **不审**，回一句要求带锚重投。机械检查前移、语义检查兜尾。

**A4 四消费方对齐（同一锚口径）。**

| 消费方                | 改成                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------- |
| 提交钩子的归属写回    | 不再需要"用当轮 trace_id 冒充链锚"，只写归属                                                    |
| 评估归档              | 链锚口径取**首轮锚**，判词查询按锚命中（同时修掉现状"链末 trace_id 查空 → 判 success"）         |
| 收口推进              | 判词消息**携带被审的 review-sha**，收口提醒直接用它，**不再反查** commit（消除 1:N 取错的假设） |
| 重放跳过 / 上下文回捞 | 按锚查 + **限定链内 + 条数/时间窗上限**（治 20 条 / 7.7 万字符）                                |

**A5 链内角色声明（`chainRole`：`first` | `followup`）。** 审查类投递**必须显式声明本跳是建链还是链内更新**。它**不是锚**——答不了"返到哪条链"（那仍从继承来）；它是**对账位**，用来抓两个今天正在静默通过的矛盾：

| 声明       | 与结构推导冲突的情形       | 今天的行为 | 有声明后 |
| ---------- | -------------------------- | ---------- | -------- |
| `first`    | 触发消息已带锚（链已存在） | 静默挂错链 | 入口拒绝 |
| `followup` | 锚为空（漏带）             | 静默开新链 | 入口拒绝 |

- **必填**：审查类投递缺 `chainRole` → 400，与缺锚同属主闸（A3）。
- **裁决权**：链归属**以结构推导为准**（该链上是否已有审查请求消息），`chainRole` 只作对账；两者冲突 → 拒绝，不猜测、不静默择一。
- **降级**：结构推导查不动（超时 / 接口失败）→ 以声明为准并记日志，**不拒绝、不静默改变归属**。

### B 投递与兜底

**B1 钩子降级。** 提交钩子**不再投递审查请求**，只保留两件事：① commit ↔ 执行的归属写回（现有 uuid 反查路径）；② **无归属的提交（手动提交）直接补投**——用户已明示"手动提交会落掉审查，补上没问题"。

**B2 兜底移位（本 spec 的实质修正）。** 兜底判定落在**执行收尾侧**，判据三分支：

```
本执行是否产出 commit（归属已写回）
  ├─ 否  → 静默（纯调查/对话单）
  └─ 是  → 本执行是否已投递审查请求
             ├─ 已投 → 静默
             └─ 未投 → 补投（兜底）
```

**B3 降级语义（钉死）。** 判据任何一步查不动（超时 / 接口失败 / 报错）→ **一律补投**，不许静默吞。宁可多投一条，不可少审一单。

**B4 钩子文件形态。** `.husky/post-commit` 入口**保留**，不删文件——它仍是"手动提交"这条边界的唯一触发点。

### C 审查流程升级

**C1 新建 `request-review` 技能。** 参照 clowder-ai 的 `request-review` 形式，**砍掉三块不适用内容**：沙盒路径/端口/启动命令（猫咖审查在会话内）、跨家族 reviewer 匹配与"三猫不自审"（猫咖只有一只审查猫）、PR 落 verdict（猫咖收敛在店长收口）。

**C2 交接文档搬进技能。** 复用现成的机械生成（钩子里的文件清单 + Reviewer Checklist 部分），由实施猫在提交后按技能生成草稿、补填要点、再投递。**触发权从钩子交回给猫**。

**C3 前置门槛（少轮次的主要杠杆，不是模板）。** 采用 clowder 的 BLOCKED 语义：前置条件不满足则**审查请求根本发不出去**（测试未绿 / 无原始需求可引用 / 未声明 ownership / 前端未真机自证等）。模板只让审查者读得快，门槛才减轮次。

**C4 两条轮次规则。** ① 第二轮起出现**同型 finding** → 作者强制做 failure-mode audit（自己先扫全 diff 再修），治"改一个冒三个"；② 同一对象审到**第三轮** → 停手升级到需求/方案层，治"每轮都诚实修好、二十轮才合入"。

**C5 判词三档。** 审查结论从 ✅/⚠️ 两档扩为 ✅ / ⚠️ / **COMMENT**——COMMENT 为**非阻断**：不阻断收口、**不产生新链**。现状把低严重度观察项打成 ⚠️，每一条都起一轮，这是可观的轮次浪费。三档口径同时是审查猫的输出契约。

### D 文案对齐

**D1** 铁律、`quality-gate` 技能、system prompt 中所有"提交后由 post-commit hook 自动触发审查"的表述，改为「**由 Agent 自己投递，建议使用 `request-review`**」。
**D2** 投递形态同步固化：投递必须带锚；返工在同一条链上补「review-sha 更新 + 变更摘要」，**不另起一链**。

## 五、测试决策

**好测试的判据**：只断言外部行为——"投了几条"、"查得到查不到"、"400 还是 200"，不断言内部字段名或实现路径。链锚改造的验收面天然是行为型的（这条链的判词查得到 / 收口提醒的 sha 正确），不需要窥探实现。

**缝（seams）——优先用现有缝，数量越少越好**：

| #   | 缝                           | 位置                       | 测什么                                                                                                            | prior art                                                                         |
| --- | ---------------------------- | -------------------------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 1   | **投递入口**（最高缝，主缝） | 消息入库边界               | agent 缺锚 → 400；带锚 → 原样落库；用户空锚 → 允许；审查类缺 `chainRole` → 400；`chainRole` 与结构推导冲突 → 拒绝 | 组装式模块测试（真实 SQLite + 捕获 handler），`connectors/socketio.test.ts` 范式  |
| 2   | **执行收尾**                 | 执行结束判定               | 三分支：无 commit → 静默；有 commit 已投 → 静默；有 commit 未投 → 补投                                            | 模块测试（只 mock 边界），`execution/serial.test.ts`、`flow-advance.test.ts` 范式 |
| 3   | **提交钩子**                 | 脚本进程                   | 普通提交 → 投递 0 次；无 uuid 归属 → 投递 1 次                                                                    | CLI 级 e2e，`scripts/handoff-gen.e2e.mjs` 范式                                    |
| 4   | **消费方查询对齐**           | 评估归档 / 收口推进 / 重放 | 判词按锚命中；收口提醒 sha = 被审 sha；重放不再误判"已执行"                                                       | 真实 DB 组装式，`eval/episodes.test.ts` 范式                                      |

缝 3 无法与其余合并（独立进程，跨进程边界）；缝 1 / 2 / 4 同属服务端，理想形态是**收敛到一条端到端用例**：造一条含返工的链 → 全程只投一条审查 → 四个消费方查到同一链 → 收口提醒 sha 正确。

**验收标准（行为可验证）**：

1. 连续两次提交（第二次为返工形态）→ **只投一条**审查链（复现原痛点），且该链的第二次投递只带 `review-sha` 更新 + 变更摘要，**不全量重发交接文档**；
2. 改后同一条链的判词**查得到**（现状为 0 行 → 修复后命中），评估不再判 `success`；
3. 一条链挂多个 commit 时，收口提醒里的 sha = **被审的那个**；且同一链的第二条判词**仍能投出提醒**（不被 (会话,sha) exactly-once 记账吞掉）；
4. agent 投递缺锚 → 400；用户消息空锚不受影响；
5. 手动提交（无 uuid 归属）→ 仍补投；
6. 兜底判据任一步失败 → 补投（不静默吞）；
7. 声明 `chainRole: first` 但链已存在 → 拒绝；声明 `chainRole: followup` 但锚为空 → 拒绝；审查类投递缺 `chainRole` → 400（三个方向各一例）；
8. **C 块的交付物可验证**：① 静态源断言 `request-review` 技能文本含 BLOCKED 前置门槛、R2+ 同型 finding 强制 failure-mode audit、同对象 ≥3 轮升级到需求/方案层三条规则；② 行为断言——带 `COMMENT` 档的判词**不阻断收口、不产生新链**（与 ⚠️ 的行为可区分：同一条链在 COMMENT 后仍可收口）。

## 六、不在范围内

- **视觉统一**（删除 luna猫 / vision-assist、全猫切视觉模型）——用户明示后置，涉及 DB 运行态与重启，节奏不同。
- **ds猫 调查中那两行 `task_id` 交叉互换的成因**——量级 2/882、成因未定、可能由旧构建写入；**不作为本 spec 的依据**，另立受控复现小单。
- **`query_db` 白名单缺口**（`episodes` / `review_verdicts` 不在白名单、无纯聚合通道）——挂后续。
- 具体落点文件路径与代码结构——由 `to-tickets` 切票时给出。

## 七、决策留痕

- **G** 本单**走过 grilling**（2026-09-10 起，用户逐条拍板 P1/P2/P3 及本 spec 的 D 系列）；Gate B 契约已钉死：**边界**见「六、不在范围内」／**契约**=链锚字段与 `chainRole` 形状（A1·A2·A3·A5）／**验收**见「五、验收标准」七项。
- **D1** 锚 = 首轮任务的 `task_id`，字段沿用 `messages.task_id`，不新增列、不引入 `chainId` 别名 —— 否决"新建链标识列/另立字段"（同一个东西换名，且判词域本来就按此列查）；**消息 id 别名一并否决**——它躺在同一张表同一列里，被找到的唯一途径就是 `WHERE task_id = T1`，拿它校验锚是"用下游校验上游"：锚坏则校验同处坏，锚好则它什么也没多证明（同义反复），且首轮投递那一刻链上尚无审查请求，存在性校验对首轮天然失效。
- **D2** `taskId || traceId` 中的 `|| traceId` 支**降级为首轮锚生成**，不再是"漏带逃生舱"：首轮锚由入库时显式写入（`insertUserMessage` 落 `taskId || traceId`，与已经交给本轮执行的同一个 `traceId`），"空"的成因靠**必填门槛**收窄为真首轮 —— 否决"换列"（列没错，缺的是把已生成的值落对地方 + 强制携带）。
- **D3** 主闸落**投递入口**（400，零 LLM 成本），审查猫仅作语义次闸 —— 否决"只在审查猫设门槛"（要烧一轮执行读完文档才发现缺字段）。
- **D4** 兜底判定从 **commit 时刻移到执行收尾侧** —— 依据：投递载体是执行回复，commit 早于回复，commit 时刻该问题**无答案**；上一轮口述的"比较首轮/返工"只能降频、不能判"是否已投递"，会造成每条链首轮被重复投一次。
- **D5** 钩子保留文件但**不再投递**；无 uuid 归属（手动提交）仍补投 —— 用户明示手动提交落掉审查要补上；钩子是这条边界的唯一触发点。
- **D6** 现状 live bug（评估判 `success` 失真 + 收口错 sha / 永久吞提醒）**并入本活当验收面** —— 与叠链同源（都建立在"`task_id` 是可靠链标识"这个未验证假设上），分开修要改两遍。
- **D7** 视觉统一后置 —— 用户明示"先不动"。
- **D8** 判词三档 **COMMENT（非阻断、不起新链）** 并入本活 —— 用户要"完整生效"。
- **D9** clowder `request-review` 裁剪三块（沙盒 / 跨家族 reviewer / PR 落 verdict），保留门槛 + 两条轮次规则 —— 不适用内容搬进来会误导实施。
- **D10** 交接文档（`to-spec` 产物的**传输形态**，非本 spec 内容）由钩子机械生成改为**技能内生成** —— 机械部分是最有价值的部分，改的是触发权归属，不是内容。
- **D11** `chainRole`（`first` / `followup`）**本轮进契约**，定位为**对账位而非锚** —— 理由：它抓的两个矛盾（声明 `first` 但链已存在、声明 `followup` 但锚为空）**今天就在静默通过**；它挂在主判据之外，加了不影响"链归属以结构推导为准"的裁决权，并补上否决消息 id 别名后空出的那个独立校验位。**不采用**"只靠结构推导、不加声明"——结构推导只能回答"链上有没有请求"，回答不了"投递者以为自己投的是哪条链"，两者不等时无人察觉。
