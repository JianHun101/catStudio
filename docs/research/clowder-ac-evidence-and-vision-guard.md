## 二、流程主轴

心智模型：**代码不值钱，对齐才值钱**。贡献的主体不是代码，是「意图文档」。

```
1. 意图   → 开 Issue（描述问题 + 为什么）
2. 立项   → maintainer 讨论 → 分配 F 编号 → 写 Feature Doc（docs/features/Fxxx.md）
3. 实现   → 按 Feature Doc 的 AC（验收标准）写代码
4. 自检   → quality-gate（对照 spec + 真实命令证据，禁止空口称完成）
5. 送审   → request-review（跨 family、附五件套、不 self-review）
6. 合入   → merge-gate（PR + remote review + squash merge 进 main）
```

**核心是第 2 步**：Feature Doc 是**单源真相**，代码是它的产物。审查优先级从高到低：**有没有 Feature Doc（没有 = 代码没有锚）→ AC 达成了吗（带证据）→ 符合五条原理吗 → 才看代码质量**。

## 三、AC 证据化（Verified = done）

贯穿全链的一条硬线：

- `NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE` —— **没有新鲜的验证证据，禁止声称完成**
- `spec checkbox 是记录工具，不是真相源` —— 声称完成/未完成前，必须核实 `git log --grep` + `gh pr list` + 实际 commit
- 每个 AC 逐项带证据勾选（commit sha / 截图 / 测试输出），`CloseGateReport` 里 `AC-A1 ✅ met — commit abc123 + test_xxx`

## 四、愿景守护

被 F041/F216/F190 等事故砸出的护栏，特别值得记录：

- **Design Gate**：UX 改动必须 operator 确认 wireframe 才准开 worktree；纯后端走猫猫讨论；架构级 → 猫猫讨论 → **operator 拍板**
- **愿景守护猫**：close 前**非作者、非 reviewer** 的第三只猫做愿景对照——「operator 最初到底要什么？交付物解决了吗？」
- **闭环只有两条路**：(A) 实做；(B) 用户显式签字的降级（cvo_signoff）。**禁止 `follow-up` / `deferred` / `next phase` 当闭环**——clowder 明文列出这些全是不合法路径

### 6.1 第三猫愿景对照的「没通过」分叉流程（重构基线）

第三猫不审代码（那是吐槽猫），它做**出发点的独立校验**——「operator 最初到底要什么？这刀交付物解决了吗？」。它「没通过」只有两个性质、走两条路线：

| 性质的失败          | 含义                              | 判定人         | 走向       |
| ------------------- | --------------------------------- | -------------- | ---------- |
| **A. 方向偏了**     | 愿景对，但这刀做错事 / 没对准目标 | 作者重对齐愿景 | 回作者改   |
| **B. 愿景本不成立** | 这刀根本不该做 / 代价远超收益     | 用户拍板       | 升用户裁决 |

**A 类 → 回作者，不进收口链**（走吐槽猫同款分流「要改的才回作者」）：

```
第三猫 ❌（方向偏了）
→ 结论分流行首@作者（要改的才回作者）
→ 作者重对齐愿景改动
→ 重新过第三猫 → ✅ 才能往下走
```

触发点在**合并前**，不是 post-commit（注：这是对 clowder 的**适配改造**——clowder 本义是 merge 后、close 前的合入后验收视角，守护验证的是已合入 main 的代码；我们猫咖语境把它前移到合并前，作出发校验阻挡合入）。这一棒**不回店长收口**——收口是「怎么合进去」的执行判断，与「方向对不对」无关；第三猫挡住时，「店长 merge」根本不启动。

**B 类 → 升用户裁决，只有两条路**（clowder 硬规矩：闭环只有 (A) 实做、(B) 用户显式签字降级，**禁止 follow-up / deferred / next phase 当闭环**）：

```
第三猫 ❌（愿景不成立，与作者各执一词）
→ 升用户裁决（request_user_action type:'choice'，二选一）
→ 用户拍：① 愿景改，作者重做；② 显式签字降级（cvo_signoff），这刀砍掉/降级
→ 只有用户签字，才把闭环划掉
```

**这是第三猫唯一碰用户的一次**——平时它悬在链外（叠加于「吐槽猫审质量 + 店长收口 + 用户放行」之上，是第四层出发验证，不取代任何一环），只有 B 类分歧才把球踢给用户，因为它没资格拍「这刀不做」。⚠️ 工具现状：`request_user_action type:'choice'` 服务端**当前暂不支持**（渲染待后续版本），6.1 引用的是**未来能力**——重构基线务必先落地该 type 或换用现有 `type:'push'`+文本通道再依赖，避免踩空。

**一句话记忆**：方向偏了→回作者改（走吐槽猫同款分流、触发在合并前）；愿景不成立→升用户裁决（choice），用户签字降级才闭环。除此之外无「follow-up / 下期再做」的合法逃逸路。店长收口在第三猫没通过时**优先级最低**——它只是「✅ 通过后」才启动的执行动作。
