# 审查标准

## P1 / P2 / P3 严重度定义

### P1 — 阻断性（必须修）

触发条件：

- **安全漏洞**：XSS、注入、越权访问、密钥泄露、`v-html` 未消毒
- **数据丢失风险**：SQLite 写入未 catch、事务未回滚、数据迁移不可逆
- **功能崩溃**：`process.exit()` 调用路径、未捕获的 Promise rejection、无限递归无断路器
- **类型安全破坏**：绕过 Zod 校验、`as any` 强制转换、API 边界无校验
- **测试破坏**：现有测试失败、测试被 skip 而非修复

修复要求：

- 立即修复，不得延迟
- 修复后重新运行完整审查周期
- 同一 P1 在 2 轮内复现 → 升级为架构问题，暂停代码修改，重新设计方案

### P2 — 必须修（不可延迟）

触发条件：

- **逻辑错误**：边界条件遗漏（空数组、null、undefined）、竞态条件、错误的状态转换
- **性能问题**：N+1 查询、重复解析/计算、阻塞主线程的操作
- **内存/资源泄漏**：未清理的定时器、未关闭的连接、未释放的 event listener
- **架构违规**：跨越 monorepo 包边界、依赖方向错误、shared 包含副作用
- **错误处理缺失**：无超时保护、无降级策略、错误被静默吞掉

修复要求：

- 在合并前修复
- 可按作者判断修复（不需要重新完整审查，除非引入新文件）
- 同一 P2 跨 3 轮未解决 → 升级为 P1

### P3 — 可选修（现场处理）

触发条件：

- **命名**：变量/函数/文件命名不够清晰
- **注释**：缺少必要注释或注释过时
- **代码风格**：与项目风格不一致但不影响功能
- **重复代码**：可提取为工具函数的小段重复
- **测试补充**：额外边界条件测试（非阻断性）

修复要求：

- 现场修或明确放弃
- **禁止写 BACKLOG** — catStudy 无 BACKLOG 跟踪机制
- 放弃的 P3 必须在审查结论中列出并说明理由

## 审查结论

审查完成后必须给出明确结论：

| 结论            | 含义                                       |
| --------------- | ------------------------------------------ |
| ✅ **可以合并** | 无 P1/P2，P3 已处理                        |
| 💬 **仅评论**   | 只有 P3 且不要求返工，**非阻断**、照常收口 |
| ⚠️ **建议修改** | 存在 P2，修复后可合并（无需重新审查）      |
| ❌ **需要重做** | 存在 P1 或设计方向错误，修复后必须重新审查 |

档位边界（**向严不向宽**）：💬 只装「不要求返工的观察项」；判不准时取严——不得把已判定的 ⚠️ 因"问题不大"改判 💬。💬 不产生新链（不触发返工循环），与 ✅ 同走收口分流。

## 双轴审查模型（code-review 方法论）

审查沿两条独立轴进行，**分开报告、禁止合并重排**：

- **Standards 轴** — 是否符合项目文档化编码规范（CODING_STANDARDS.md / CONTRIBUTING.md 等）
- **Spec 轴** — 是否忠实实现发起它的 spec/issue/PRD（无缺失、无范围蔓延、无错误实现）

一条轴通过不能豁免另一条轴。代码可以全符规范但实现错了需求（Standards 过 / Spec 挂），也可以完全按需求做但破坏项目惯例（Spec 过 / Standards 挂）。报告两轴分列，最严重问题按轴各自给出，不跨轴选一个「总冠军」。

### Standards 轴：坏味道基线（Fowler _Refactoring_ ch.3）

文档化规范优先于基线；每条坏味道是**判断标签**（「可能 Feature Envy」）不是硬违规；工具已强制的跳过。每条读「是什么 → 怎么修」，对着 diff 匹配：

- **Mysterious Name** — 名字不揭示作用/内容 → 重命名；起不出诚实的名字 = 设计模糊
- **Duplicated Code** — 同一逻辑形状在 diff 多处出现 → 提取共享形状，两处共用
- **Feature Envy** — 方法摸别的对象数据多于自己的 → 移到所羡慕的数据上
- **Data Clumps** — 同组字段/参数总是一起出现 → 打包成类型
- **Primitive Obsession** — 基本类型/字符串代指值得成类型的领域概念 → 建小类型
- **Repeated Switches** — 对同类型的 switch/if 级联在改动中重复 → 多态或共享 map
- **Shotgun Surgery** — 一个逻辑改动散落多文件 → 收拢到一个模块
- **Divergent Change** — 一个文件因多种无关理由被改 → 按理由拆分
- **Speculative Generality** — 为 spec 不需要的抽象/参数/钩子 → 删掉，回到真实需求
- **Message Chains** — 长 `a.b().c().d()` 导航 → 藏到首对象的一个方法后
- **Middle Man** — 类/函数只是转发 → 砍掉，直接调真实目标
- **Refused Bequest** — 子类/实现者忽略或覆盖大半继承 → 放弃继承用组合

### 审查者的禁止行为

- **表演性同意**（对称于 receive-review 的禁区）——「写得不错」「lgtm」而无逐条核实，等于没审
- **只给「不够优雅」不给证据** → 每条发现附具体文件/行/hunk，能引用规范/坏味道名就引用
- **硬违规与判断标签混为一谈** → 文档化规范违规可报硬；坏味道永远是判断，且文档规范优先于基线

## cat-study 项目特有 Diff 检查点

通用坏味道基线之上，cat-study 有一套**项目特有 diff 检查点**（CJK 正则边界、`skill_modules` 清空、`retractionRequests`/`activeStreams` 清理配对、`agentSlots.currentTriggerMessageId`、`.push-gate` 拦截、`parseInt('0')` 零值吞、`seed.ts --reset` FK 顺序、Socket.IO room 前缀一致性、Window ② 撤回保护等）。审查扫描 diff 时按改动范围选择性套用——**逐条清单的活载体是 `scripts/handoff-gen.mjs` 的 `buildChecklistSection(changeTypes)`**：它按实际 diff 的改动类型动态生成检查项，写进交接文档 `## 5. Reviewer Checklist` 投给审查者。本文件聚焦审查标准定义，不另存逐条清单（静态清单副本已随 refs 层收敛删除——一份会漂移的副本只会让「按哪个为准」无解）。
